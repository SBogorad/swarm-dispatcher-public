# Swarm Ops Console — демонстрационный контур координации агентов

Кабина для показа инженерам, архитекторам и руководству: поставить цель,
увидеть, как движок декомпозирует её в граф задач, как задачи проходят
`pending → ready → leased → review → done`, кто из агентов что держит и что
записано в неизменяемом журнале (хэш-цепочка). Всё — из базы движка.

Никакого терминала с `cargo test` и таблиц PostgreSQL на экране: только
канбан, узлы роя и результаты.

## Запуск одной командой

```bash
./scripts/start_demo.sh            # поднять и открыть браузер
./scripts/start_demo.sh --no-open  # без браузера
./scripts/start_demo.sh --down     # остановить и удалить (включая БД)
```

Состав поднимается из `docker-compose.demo.yml` (боевой `docker-compose.yml`
не затрагивается: свои volume и порты):

| сервис | роль |
|---|---|
| `postgres` | схема v0 (единый источник истины) + `demo/schema_extras.sql` |
| `demo-bridge` | FastAPI: цель → граф задач, канбан/карточка/журнал (порт 8080) |
| `agent-1/2/3` | агенты-исполнители: забирают задачи по SQL-протоколу |
| `demo-reviewer` | строгий review-gate (F2) |
| `demo-scheduler` | `promote_ready` / `reclaim_expired` (сторож) |
| `demo-ui` | Swarm Ops Console (Streamlit, порт 8501) |
| `demo-init` | регистрация агентов |

## Что происходит при демонстрации

1. Ведущий вводит цель, например:
   «Проанализировать модуль авторизации, составить план рефакторинга,
   написать юнит-тесты и провести аудит безопасности».
2. Мост декомпозирует цель в граф задач и вносит его в движок публичными
   `add_task` + `add_dep` — ровно так же, как это делает `swarm-planner`.
3. Сторож переводит корень `pending → ready`; агент берёт задачу по
   `claim_task` (fencing-аренда по `lease_epoch`).
4. Когда зависимость завершена, движок сам переводит следующую задачу в
   `ready` — коллеги видят, как граф «оживает» на глазах.
5. Ревьюер проводит каждую задачу через строгий review-gate; задача → `done`
   только при совпадении набора проверок с контрактом.
6. Консоль рисует канбан, узлы роя, карточку задачи (аренда, эпоха, бюджет,
   контракт), артефакт и журнал с хэш-цепочкой (`verify_chain`).

## Честная архитектура: движок, ядро и демо-слой

Это важно проговорить на встрече, чтобы не выдать желаемое за действительное.

**Ядро (работает по-настоящему).** Мост и агенты говорят с движком ровно теми
же публичными SQL-функциями, что и Rust-бинaри: `register_worker`, `add_task`,
`add_dep`, `claim_task`, `heartbeat`, `save_artifact`, `complete_task`,
`submit_review`, `fail_task`, `promote_ready`, `reclaim_expired`. Поэтому в
демо реальны: декомпозиция в DAG с зависимостями, промоушен по готовности,
fencing по `lease_epoch`, отзыв аренд сторожем, хэш-цепочка событий,
запрет self-review (RV002), строгая проверка набора `checks` по ключам
контракта (RV003), реестр типов проверок (`cmd|test|unit|lint|manual`).

**Настоящее ядро проверено на этой же БД.** К демо-базе подключаются и
настоящие Rust-бинарники (образ `swarm-core:local`): `swarm-planner` создаёт
граф через LLM, `swarm-worker` забирает и исполняет задачи. Это подтверждено
прогоном (см. раздел «Проверки»). Для них нужна функция `task_status()`,
которую и добавляет `demo/schema_extras.sql`.

**Демо-слой (осознанное упрощение).**
- Агенты демо — Python-процессы, а не Rust `swarm-worker`. Причина: в
  изолированном контуре нет достижимой LLM (Ollama слушает loopback хоста,
  из контейнеров недоступна), поэтому артефакт вырабатывает детерминированный
  rule-based агент (`lib/agent.py`) — тот самый fallback из ТЗ «для
  гарантированной демонстрации без интернета». Координацию при этом делает
  движок, а не агент.
- Сторож — отдельный Python-цикл, дергающий те же две функции, что и Rust
  `swarm-watchdog`.
- Декомпозиция в `lib/decompose.py` — локальная rule-based (анализ →
  исполнение → проверка), а не LLM-планировщик. Форма `add_task`+`add_dep`
  идентична планировщику, поэтому зависимости и промоушен считает движок.

## Проверки (что можно перепроверить)

```bash
# Стенд поднят?
curl -s http://127.0.0.1:8080/healthz
curl -s http://127.0.0.1:8080/board | head

# Поставить цель и посмотреть граф
curl -s -X POST http://127.0.0.1:8080/goals \
  --data-urlencode "goal=Проанализировать модуль авторизации и написать тесты"

# Карточка задачи: аренда, контракт, хэш-цепочка, verify_chain
curl -s "http://127.0.0.1:8080/tasks/<task_id>"
curl -s "http://127.0.0.1:8080/tasks/<task_id>/chain-verify"
```

## Переменные окружения

| переменная | смысл | по умолчанию |
|---|---|---|
| `DEMO_DB_PASSWORD` | пароль БД демо | `swarm` |
| `DEMO_UI_PORT` / `DEMO_API_PORT` | порты консоли / моста | `8501` / `8080` |
| `DEMO_LEASE_SEC` | аренда задачи, с | `120` |
| `DEMO_POLL_SEC` | период опроса задач агентом, с | `1.0` |
| `DEMO_SCHED_INTERVAL` | период сторожа, с | `1.0` |

## Структура

```
demo/
  lib/decompose.py          # цель → граф задач (add_task/add_dep, как planner)
  lib/agent.py              # агент-исполнитель: артефакт по контракту
  db/client.py              # клиент публичного SQL-протокола движка
  engine/worker.py          # агент: claim → артефакт → save_artifact → complete
  engine/reviewer.py        # ревьюер: строгий review-gate
  engine/scheduler.py       # promote_ready / reclaim_expired
  bridge/api.py             # FastAPI-мост (цель → граф, витрина)
  ui/app.py                 # Swarm Ops Console (Streamlit)
  schema_extras.sql         # task_status() для настоящих Rust-бинарников
docker-compose.demo.yml
scripts/start_demo.sh
```

## Ограничения демо-контура

- Пароль БД по умолчанию `swarm` — **только для демо в закрытом контуре**;
  для реального показа задайте `DEMO_DB_PASSWORD`.
- Порты 8080/8501 отдаются на хост; для показа «из контура» ограничьте доступ
  (bind на нужный интерфейс или обратный прокси).
- Стенд не претендует на роль боевого контура: это витрина над тем же
  движком, с честно разделёнными демо- и ядровыми частями.

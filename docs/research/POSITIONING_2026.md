## 1. Базовая технологическая гипотеза

> **Гипотеза (2026-10):**  
> В открытом доступе и промышленной практике **отсутствует готовое коробочное решение**, реализующее легковесную пакетную оркестрацию децентрализованной группы автономных ИИ-агентов на гетерогенном и слабом оборудовании (потребительские ПК, локальные квантованные модели, CPU-ноды) по принципу **«Task-level MoE with Lease-based FSM»** с PostgreSQL как единственным источником истины, монотонными токенами ограждения (`lease_epoch`), защитой от зомби-воркеров и криптографически верифицируемым аудитом без привлечения тяжеловесных платформ распределенного исполнения (Temporal, Ray, Kubernetes, Kafka, Redis).

Эта гипотеза датирована. Через 6–12 месяцев развитие открытых инструментов может сделать ее устаревшей, если появятся нативные плагины для Temporal/Postgres или специализированные агентские диспетчеры. Ниже приведен детальный срез того, как смежные задачи решаются в мире на текущий момент.

## 2. Анализ существующих мировых подходов

Мировая индустрия решает задачи координации через три непересекающихся технологических стека:

### Стек A. Долговечное выполнение и очереди на PostgreSQL (Durable Execution & Queues)

1. **Транзакционные очереди в PostgreSQL (River, Oban, pg-boss, Graphile Worker):**
   - *Как устроено:* Конкурентный захват пачек задач через `FOR UPDATE SKIP LOCKED`, поддержка очередей с приоритетами, повторные попытки (retries with backoff).
   - *Почему не закрывает задачу:* Они оперируют простыми изолированными джобами (background jobs). В них отсутствует понятие динамического ориентированного графа подзадач (DAG), состязательного рецензирования артефактов (Adversarial Review), токеномики LLM и изоляции промпт-инъекций.
2. **Платформы долговечного выполнения (Temporal, Restate, Hatchet):**
   - *Temporal / Cadence:* Промышленный стандарт распределенной надежности. Использует модель детерминированного воспроизведения истории событий (*Event History Replay*). Для вероятностных генеративных моделей (LLM) это создает проблему: повторный прогон шага без детерминированного кэширования дает иной результат, ломая гарантии. Кроме того, Temporal требует отдельного кластера и сервисов координации.
   - *Restate:* Легковесный журнальный рантайм. Применяет механизм *Epoch Fencing*, концептуально идентичный `lease_epoch` в `swarm-dispatcher`. Однако Restate предназначен для микросервисных RPC-цепочек, а не агентского управления.
   - *DBOS и Absurd Workflows (Armin Ronacher, 2025–2026):* Инициатива переноса концепции Durable Workflows внутрь PostgreSQL. Демонстрирует растущий глобальный консенсус о том, что для надежного сохранения состояния база данных превосходит связки «Redis + Celery».

### Стек B. Мультиагентные и канбан-фреймворки (Agent Frameworks & Swarms)

1. **LangGraph (LangChain):**
   - Доминирующий стандарт построения циклических агентных графов (Pregel architecture).
   - Поддерживает контрольные точки в PostgreSQL (`PostgresSaver`) и приостановку для участия человека (`interrupt`).
   - *Ограничение:* Спроектирован для исполнения внутри одного процесса или одного контейнера. В нем нет распределенного планировщика физических узлов с сопоставлением аппаратных возможностей (`needs` vs `capabilities`). Падение контейнера требует полного перезапуска воркфлоу внешним супервизором.
2. **AutoGen (Microsoft / AG2), CrewAI, MetaGPT:**
   - Ориентированы на диалоговые цепочки (Conversational Swarms) в оперативной памяти.
   - Рассчитаны на облачные API с минимальной задержкой. Не обладают транзакционными конечными автоматами, защитой от зомби-процессов и персистентным аудитом в базе данных.
3. **Nous Research Hermes Agent (Kanban Worker Lanes, 2026):**
   - Наиболее близкий концептуальный аналог. Использует доску на SQLite с дорожками воркеров (`worker lanes`), декомпозицию и навык состязательного ревью (`sdlc-review`).
   - *Ограничение:* Решение строго оптимизировано для персонального использования на одном локальном хосте и не рассчитано на распределение задач по сети.
4. **Veritas Kanban (Brad Groux, 2026):**
   - Автоматизация рабочих процессов через канбан и `git worktree`.
   - *Ограничение:* Обеспечивает изоляцию файловой системы веток Git, но не изолирует системные привилегии процессов в ОС и не решает задачу удаленного кластера.

### Стек C. Распределенный инференс на потребительском оборудовании

1. **Petals (BigScience) / Parallax:**
   - Децентрализованное разделение слоев одной модели между участниками сети через DHT (Swarm Parallelism).
   - *Различие в задаче:* Petals решает задачу **тензорного параллелизма одного инференса**. Из-за необходимости частой пересылки промежуточных активаций через сеть система крайне чувствительна к задержкам (latency-bound).
2. **Exo (2025–2026):**
   - Объединение компьютеров (Mac Studio, Linux) в кластер для запуска модели целиком через MLX/RDMA.
   - Это уровень выполнения нейросети, а не уровень оркестрации задач и инструментов.

## 3. Архитектурная ниша Swarm Dispatcher

`swarm-dispatcher` занимает самостоятельную нишу: **Task-level Mixture-of-Experts (MoE) с конечным автоматом на базе аренд**.

Вместо медленного разрезания весов одной нейросети через сетевые сокеты, система декомпозирует сложную 8-часовую задачу на контрактные подзадачи и распределяет их по пулу разнородных узлов:
- Легкие задачи анализа, разметки и декомпозиции забирают слабые CPU/малые модели (Haiku / 8B).
- Сложные задачи кодогенерации уходят на узлы с выделенными GPU и reasoning-моделями.
- Задачи верификации, сборки и тестов забирают узлы с дисковыми ресурсами и компиляторами.

```
       [Пользовательская задача (8h batch)]
                       │
             [Planner / Декомпозиция]
                       │
       ┌───────────────┴───────────────┐
       ▼                               ▼
[Подзадача 1: Сборка]        [Подзадача 2: Код]
(узел: быстрый NVMe, CPU)   (узел: локальный GPU)
       │                               │
       └───────────────┬───────────────┘
                       ▼
            [Подзадача 3: Рецензия]
           (узел: кросс-вендорная LLM)
                       │
            [Криптографический Gate]
                       │
                    [Done]
```

### Ключевые преимущества подхода:
1. **Толерантность к задержкам:** Обмен между машинами происходит только на границах задач (передача артефактов и контрольных сумм), а не на каждом токене.
2. **Автономность узлов:** Сбои сети или временное падение узла не ломают общий кластер благодаря механизму `reclaim_expired` и монотонному счетчику `lease_epoch`.
3. **Нулевой оверхед по инфраструктуре:** Отсутствие брокеров очередей и внешних координаторов снижает требования к администрированию до наличия одного экземпляра PostgreSQL.

## 4. Рекомендации по интеграции мировых практик в дорожную карту проекта

1. **Компиляционный барьер для недоверенных инструментов:** Полное отключение недоверенного агентского цикла (`agent_loop`) в релизном бинарнике до проведения глубокого аудита безопасности песочницы.
2. **Переход к контентно-адресуемому S3-хранилищу (CAS):** Замена локальных путей `/var/swarm/artifacts` на S3-совместимые пути с ключом `sha256/<digest>` (MinIO / Ceph), обеспечивающее физический обмен файлами между машинами.
3. **Паттерн Transactional Outbox:** Разделение коммита транзакции в базе данных и побочных эффектов воркера (запись на диск, сетевые уведомления) для предотвращения рассинхронизации.
4. **Абсолютные лимиты удержания аренды (Max Lease Timeout):** Ограничение максимального времени удержания задачи независимо от частоты heartbeat-запросов.

## Шаг 1 (ближайший): Python-обёртка по ТЗ

**Артефакт:** `TZ_executor_v0.md` — уже готов.

**Что делает агент-исполнитель:**

  SQL-функциями с маппингом SQLSTATE в исключения.

- `swarm/worker_stub.py` — демонстрационный воркер без LLM.
- `swarm/cli.py` — seed / status / review / reopen / unblock.
- `sql/roles.sql` — разделение прав между ролями.

- Тесты: `test_wrapper.py`, `test_roles.py`, `test_watchdog.py`, `test_e2e.py`.

**Критерий готовности:**
1. `pytest -q` — 26 passed (из `test_v0.py`) + новые тесты без пропусков.
2. `docker compose up -d --build` поднимает Postgres + watchdog + 2 воркера.
3. End-to-end сценарий (seed → падение → reclaim → выполнение) работает за 60 сек.
4. Нет `:latest`, нет паролей в репозитории.

**После приёмки** — коммит в репозиторий с тегом `v0.1`.

## Шаг 2: Нагрузочный тест

**Зачем.** Инварианты проверены, но throughput неизвестен. Для решения
«ставить ли на production» нужны цифры.

**Что делаем:**
- Сценарий: 1000 задач, граф глубиной 20, ширина 10 на узел.
- 50 воркеров параллельно, каждый забирает задачу, спит 100 мс, пишет артефакт.
- Замер: throughput (`tasks/sec`), latency claim (p50, p95, p99), поведение
  recursive cascade на графе 1000 узлов.
- Проверка: `verify_chain` проходит на всех 1000 задач после завершения.

**Артефакт:** `bench/load_test.py`, `bench/RESULTS.md` с графиками и таблицей.

**Что даст:**
- Материал для публикации.
- Понятные границы применимости (например, «до 10 000 задач в одном
  графе», «до 100 воркеров на одном Postgres»).

## Шаг 3: Публикация

**Формат — что-то из:**
- Технический отчёт (arXiv / препринт на Zenodo).
- Статья на Habr / Medium с кодом и результатами.
- Доклад на конференции (DevOps / SRE / AI Infra).

**Структура:**
1. Постановка: почему batch-задачи на слабом железе важны.
2. Проблема: канбан — Control Plane, не Durable Execution Engine.
3. Решение: Postgres-first, fencing tokens, хэш-цепочки.
4. Реализация: 5 таблиц, 14 функций, 26+ тестов.
5. Результаты: throughput, latency, поведение под нагрузкой.
6. Уроки: паттерны ошибок, метод проверки тестов «7 поломок».
7. Ограничения и направления развития.

**Открытый код:** GitHub-репозиторий под MIT или Apache-2.0.

## Отложено (не в ближайших планах)

| Что | Почему отложено |
|-----|-----------------|
| Веб-интерфейс | Пользователи могут работать через CLI |
| Реальный LLM в воркере | Демонстрация не требует LLM |
| Rate limiting | Не нужен без публичного endpoint |
| Backup / restore | Нужен перед production, не для прототипа |
| SAST / DAST | Требует CI-инфраструктуры |
| Deadlock prevention | SQL-функции короткие, deadlock маловероятен |
| User management | Trust Registry в v2 |

## Что может пойти не так

1. **Публичное API** — потребует rate limiting, OAuth, мультитенантность.
   Это v2, не v0.
2. **Рост графа до миллионов задач** — Postgres может не справиться.
   Нужно шардирование по `root_id`.
3. **Долгие транзакции** — если воркер случайно откроет транзакцию на
   inference, Postgres захлебнётся. В v0 это архитектурно невозможно (все
   транзакции короткие), но в v1 нужен контроль.
4. **Проблемы с `lease_epoch`** — если воркеры будут злоупотреблять
   продлением аренды, старые операции могут «зависнуть». Нужна политика:
   максимальное время жизни аренды.
5. **Рецензент «другой модели»** — в v0 это просто «не автор артефакта».
   Для настоящей состязательности нужно хранить `family` модели в воркере.

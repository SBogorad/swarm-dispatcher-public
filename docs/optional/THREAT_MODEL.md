# Модель угроз и криптографическая верификация

Содержит модель угроз (9 векторов) и описание механизмов

## 1. Девять векторов атак

| Вектор | Механизм | Последствия | Недостаточная защита | Рекомендуемый контроль |
|--------|----------|-------------|----------------------|------------------------|
| **Indirect Prompt Injection** | Внедрение инструкций в issue, README или сторонний сайт | Агент переопределяет системную цель и выполняет команды злоумышленника | Добавление фраз «игнорируй сторонние инструкции» | Структурированное разделение системного и пользовательского каналов на уровне API, семантические Prompt Guards |
| **Confused Deputy Attack** | Манипуляция моделью для вызова штатного MCP-инструмента | Несанкционированное удаление веток, утечка данных через валидный инструмент | Флаг `destructiveHint` в описании схемы | Независимый Policy Engine (OPA/OpenFGA) с проверкой субъекта, ресурса, действия и контекста |
| **Утечка секретов и токенов** | Попадание переменных окружения в историю сообщений или diff | Публикация API-ключей в тикетах, баг-трекерах, публичных ветках | Инструкция модели «не показывай пароли» | Credential Brokering, маскирование энтропии в сетевом шлюзе (Redaction), изоляция `.env` |
| **Подмена артефакта (TOCTOU)** | Модификация исходного кода воркером после завершения фазы Review | Слияние вредоносного или непроверенного кода в основную ветку | Проверка статуса карточки на канбан-доске | Валидация хэша: слияние блокируется, если Git-хэш коммита отличается от подписанного в Review |
| **Replay-атаки на вебхуки** | Повторная отправка перехваченного вебхука | Повторное выполнение дорогостоящего цикла и списание бюджета | Отсутствие проверки свежести сообщений | HMAC-подпись заголовков, включение временных меток и валидация одноразовых nonce через Redis |
| **Компрометация Event Log** | Модификация или очистка журнала аудита скомпрометированным агентом | Сокрытие следов деструктивных действий, потеря доказательной базы | Запись в стандартные таблицы БД без разграничения привилегий | Привилегии Append-Only (`REVOKE UPDATE, DELETE ON task_audit_log`), экспорт в WORM-хранилище (S3 Object Lock) |
| **Утечка данных в OpenTelemetry** | Попадание секретов и PII в спаны телеметрии | Утечка конфиденциальных данных в сторонние APM-системы | Экспорт полных промптов в стандартных спанах OTel | Запрет включения тела сообщений в спаны по умолчанию, стриминговое маскирование (Regex Redactor) |
| **Sandbox Escape / Хостовый взлом** | Агент запускает вредоносный код компиляции или системные вызовы | Доступ к сокетам Docker, чтение хостовой файловой системы | Изоляция через `git worktree` | Запуск в непривилегированных контейнерах (`cap_drop: ALL`, `read_only: true`, `no-new-privileges`) или microVM |
| **MCP Supply Chain Attack** | Подмена зависимостей, вредоносный сторонний MCP-сервер | Перехват трафика вызовов инструментов, выполнение произвольного кода | Доверие непроверенным реестрам npm/pip | Пиннинг версий, криптографическая проверка подписей манифестов через Sigstore / Cosign |

## 2. Сравнение сред изоляции (Sandbox Matrix)

| Технология | Уровень изоляции | Накладные расходы | Сетевая изоляция | Применимость для ИИ-агентов |
|------------|-----------------|-------------------|------------------|------------------------------|
| **Git worktree** | Файловая система (только ветки) | Минимальные (доли секунды) | Отсутствует (доступ к локальной сети хоста) | Недостаточна как изолирующий контур безопасности |
| **WASI / WebAssembly** | Байт-код в песочнице рантайма | Сверхнизкие (миллисекунды) | Полная (строго бессерверные сокеты) | Ограничена: многие инженерные утилиты и CLI не компилируются в WASM |
| **Docker Hardened** | Linux Namespaces, Cgroups, Seccomp | Низкие (0.5–2 сек) | Настраиваемая (Deny-by-Default) | Рекомендуемый базовый стандарт при `cap_drop: ALL`, `read_only: true` |
| **gVisor (runsc)** | Перехват системных вызовов в пространстве пользователя | Умеренные (1–3 сек) | Полная (виртуализированный сетевой стек) | Высокая: надёжная защита ядра Linux от уязвимостей компиляторов и скриптов |
| **MicroVM (Firecracker)** | Аппаратная виртуализация KVM | Низкие (5–10 мс) | Полная аппаратная изоляция интерфейсов | Максимальная степень защиты для промышленного запуска недоверенного кода |

**Ключевой вывод.** `git worktree` предотвращает конфликты слияния файлов,
но **не изолирует системные привилегии процесса ОС**. Для безопасного
запуска недоверенного кода необходим Docker Hardened, gVisor или Firecracker.

## 3. Криптографическая верификация согласований

### 3.1. Разделение ответственности

Документ фиксирует **три независимых компонента**, каждый решает
свою задачу:

| Компонент | Что делает | Чего не делает |
|-----------|-----------|----------------|
| **OPA (Open Policy Agent)** | Авторизация: имеет ли роль/субъект право на действие | Не верифицирует криптографические подписи |
| **CryptoVerifier** | Математическая проверка Ed25519-подписи | Не принимает решение о правах |
| **Trust Registry** | Хранит публичные ключи approver-ов, поддерживает отзыв (`revoked_at`) | Не проверяет подписи |

**Почему разделение критично.** Концептуальная ошибка — пытаться
верифицировать Ed25519 через OPA. Rego не имеет встроенных функций
асимметричной криптографии. OPA может проверить **наличие**, **формат**,
**срок действия** и **совпадение хэша** — но не валидность самой подписи.

### 3.2. Trust Registry

```sql
CREATE TABLE approvers (
    id             VARCHAR(64) NOT NULL,
    tenant_id      VARCHAR(64) NOT NULL,
    role           VARCHAR(32) NOT NULL,
    public_key_b64 TEXT NOT NULL,
    revoked_at     BIGINT,
    PRIMARY KEY (tenant_id, id)
);
```

Ключи привязаны к идентификатору оператора, а не передаются в запросе.
Проверка при верификации:

· approver_id существует в реестре;
· revoked_at IS NULL OR revoked_at > now();
· публичный ключ соответствует approver_id.

3.3. Approvals Registry (защита от replay)

```sql
CREATE TABLE approvals (
    event_id      VARCHAR(64) NOT NULL,
    tenant_id     VARCHAR(64) NOT NULL,
    task_id       UUID NOT NULL,
    artifact_hash VARCHAR(64) NOT NULL,
    approver_id   VARCHAR(64) NOT NULL,
    signature     TEXT NOT NULL,
    expires_at    BIGINT NOT NULL,
    created_at    BIGINT NOT NULL,
    used_at       BIGINT,
    revoked_at    BIGINT,
    PRIMARY KEY (tenant_id, event_id)
);
```

Три поля закрывают три класса атак:

· used_at — защита от replay. Одно согласование — один переход.
· revoked_at — оператор может отозвать мандат до использования.
· artifact_hash — согласование привязано к конкретной версии артефакта,
  а не к задаче в целом.

3.4. CryptoVerifier (Ed25519)

```python
class CryptoVerifier:
    @staticmethod
    def verify_ed25519_signature(public_key_b64, signature_b64, message_bytes):
        try:
            public_key_bytes = base64.b64decode(public_key_b64)
            signature_bytes = base64.b64decode(signature_b64)
            public_key = ed25519.Ed25519PublicKey.from_public_bytes(public_key_bytes)
            public_key.verify(signature_bytes, message_bytes)
            return True
        except (ValueError, InvalidSignature):
            return False

    @classmethod
    def verify_approval_token(cls, public_key_b64, tenant_id, task_id,
                              artifact_hash, approval_event_id, expires_at,
                              signature_b64):
        canonical_msg = (
            f"{tenant_id}:{task_id}:{artifact_hash}:"
            f"{approval_event_id}:{expires_at}"
        ).encode('utf-8')
        return cls.verify_ed25519_signature(
            public_key_b64, signature_b64, canonical_msg
        )
```

Каноническое представление (canonical_msg) включает:

· tenant_id — защита от подмены тенанта;
· task_id — защита от переноса согласования на другую задачу;
· artifact_hash — защита от TOCTOU (подмена артефакта после ревью);
· approval_event_id — защита от replay;
· expires_at — защита от использования устаревшего мандата.

3.6. Криптографическая фиксация цепочки исполнения

В момент перехода задачи в Review или Done платформа генерирует
неизменяемую хэш-структуру (SHA-256):

```
H_run = SHA256(
    H_prompt
    || H_model_spec
    || H_tools
    || H_input_diff
    || H_output
)
```

Компоненты:

1. Промпт и системные инструкции (H_prompt) — хэш системного
   промпта, роли агента, инструкций рабочего пространства, постановки задачи.
2. Спецификация модели (H_model_spec) — уникальный ID модели,
   контрольная сумма весов (для локальных моделей), temperature, seed,
   system_fingerprint провайдера.
3. Спецификация среды и инструментов (H_tools) — снапшот JSON-схем
   всех MCP-инструментов, доступных агенту, с фиксацией версий серверов.
4. Входное состояние (H_input_diff) — Git commit hash исходного
   репозитория и базового рабочего дерева.
5. Цифровая подпись агента — подпись полученного хэша асимметричным
   ключом исполнителя (например, ED25519 в связке с OIDC-токенами).

4. Разграничение технической и юридической ответственности

Разделение ролей формализует ответственность за инциденты.

· Ответственность за постановку (Спецификатор / Владелец). Если агент
  корректно выполнил критерии приёмки, но реализация привела к бизнес-ошибке,
  ответственность несёт автор задачи или модель-декомпозитор фазы Triage.
· Ответственность за реализацию (Агент-исполнитель). Определяется как
  расхождение между контрактом задачи и фактическим патчем кода.
· Ответственность за валидацию (Агент-рецензент / Человек). Переход
  в колонку Done — юридический факт приёмки. Если код утверждён человеком
  через HITL-интерфейс, ответственность за внедрение уязвимости в продакшн
  переходит на сотрудника, подписавшего карточку.

Все события фиксируются в неизменяемом журнале аудита (append-only log
с хэш-цепочкой) с возможностью экспорта для расследования инцидентов ИБ.

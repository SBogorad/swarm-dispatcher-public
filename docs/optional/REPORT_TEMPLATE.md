## Аннотация

Описываем архитектуру распределённого оркестратора задач, оптимизированного
для сценариев, где железо слабое и гетерогенное, latency не критична, но
важна выполнимость и отказоустойчивость. Ключевые механизмы: Postgres как
единственный источник истины, fencing tokens для защиты от зомби-воркеров,
хэш-цепочка событий для tamper-evidence, Guarded FSM для валидации
переходов. Реализация на Rust, ~1500 строк кода, 26 SQL-тестов, 8 unit +
5 integration Rust-тестов. Проверено на двух средах: Docker Compose и
native user-space.

**Ключевые слова:** распределённая оркестрация, Postgres, fencing token,
idempotency, Guarded FSM, Rust.

## 1. Введение

### 1.1. Проблема

Современные системы оркестрации ИИ-агентов (Temporal, Restate, Airflow)
ориентированы на **скорость** и **облачную инфраструктуру**. Они требуют:

- Отдельного сервера для движка.
- Знания DSL / Python API.
- Миграций.
- Kubernetes / Docker.

Это создаёт барьер для **маленьких команд** и **исследовательских сред**,
где задача — выполнить batch на слабом гетерогенном железе за 8 часов, а
не выдать ответ за миллисекунды.

### 1.2. Наша постановка

Целевой сценарий:

- **N слабых машин** (16 ГБ RAM, без GPU).
- **M задач**, разбитых на 20–50 подзадач.
- **Batch-режим** (8 часов на задачу — приемлемо).
- **Отказоустойчивость**: падение воркера не разрушает работу.
- **Наблюдаемость**: видеть, кто взял, что сделано.
- **Формальные инварианты**: fencing, idempotency, audit.

### 1.3. Наш подход

Postgres-first диспетчер. Один источник истины. Rust для инфраструктуры.
Без Redis, без внешних очередей.

## 2. Архитектура

### 2.1. Control Plane vs Data Plane

- **Control Plane:** Postgres + Rust-диспетчер. Состояние задач, аренды,
  события.
- **Data Plane:** Воркеры (LLM, инструменты). Работа вне транзакций.

### 2.2. Guarded FSM

6 состояний: `pending`, `ready`, `leased`, `review`, `done`, `blocked`.
Переходы только через SQL-функции. Guards проверяют инварианты.

### 2.3. Fencing token

`tasks.lease_epoch` — монотонный счётчик. Любая запись воркера несёт epoch.
Если в БД epoch больше — запись отвергается (`LS001`).

### 2.4. Хэш-цепочка событий

`events.prev_hash` + `hash = sha256(prev_hash || payload)`. Блокировка
строки `tasks` сериализует запись.

### 2.5. Recursive cascade

При откате родителя все потомки блокируются одним запросом
(`WITH RECURSIVE`), epoch инкрементируется.

## 5. Обсуждение

### 5.1. Что работает хорошо

- Postgres как единый источник истины — простота и атомарность.
- Fencing token — решает реальную проблему зомби-воркеров.
- Хэш-цепочка — tamper-evidence без внешнего сервиса (non-repudiation — v2.0).

### 5.2. Ограничения

- Postgres — bottleneck при >1000 tasks/sec.
- Нет мультитенантности.
- Нет встроенного LLM.

### 5.3. Уроки

- **Прогнозы без компиляции неполны.** E0521 — пример.
- **Пиннинг версий не гарантирует сборку.** Транзитивные зависимости
  эволюционируют.
- **Тесты надо проверять тестами.** Метод «7 поломок».

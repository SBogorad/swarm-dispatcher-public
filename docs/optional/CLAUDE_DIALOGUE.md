# Ключевые обмены с Claude

Документ фиксирует конкретные замечания и решения, полученные в диалоге
с Claude. Цель — сохранить аргументацию, не только выводы.

---

## Обмен 1: критический аудит v14 (8 пунктов)

Claude нашёл 8 критических дефектов, которые я не заметил при чтении кода.

### 1. Heartbeat не продлевает аренду

**Диагноз Claude.** В `execute_tool_call` обновляется только TTL ключа в
Redis, а `lease_expires` в БД не меняется. Метода `heartbeat` в коде нет.
Задача дольше 5 минут будет «отобрана» у живого воркера.

**Что я не заметил.** Я видел `self.redis.expire(redis_key, 60)` и считал,
что этого достаточно. Но Redis-ключ — это про идемпотентность, а не про
аренду. Аренда — в `tasks.lease_expires`, и она не продлевалась.

**Решение в v0.** `heartbeat` как SQL-функция. Продлевает только действующую
аренду; истёкшую «оживить» нельзя.

### 2. Дедупликация до коммита

**Диагноз Claude.** Ключ `evt:{event_id}` пишется в Redis раньше транзакции.
Если транзакция упала, повтор с тем же `event_id` вернёт `True` как будто
всё прошло.

**Решение в v0.** Дедупликация через `UNIQUE (task_id, event_id)` в БД, в
той же транзакции, что и переход состояния. Redis убран.

### 3. Привязка согласования к артефакту дырявая

**Диагноз Claude.** Хэш в approvals сверяется с хэшем, который передал сам
вызывающий, а не с `tasks.artifact_hash`. Затем `COALESCE` перезаписывает
хэш задачи. В OPA проверка `target_artifact_hash == task.artifact_hash`
тавтологична: оба значения диспетчер берёт из одной переменной.

**Что это значит.** Это TOCTOU-атака: атакующий передаёт `artifact_hash=X`,
согласование валидно для X, потом задача получает X в качестве результата.
Хэш из approvals не связан с фактическим артефактом задачи.

**Решение в v0.** `artifact_hash` берётся из БД, не из параметра. OPA-проверка
`target_artifact_hash == task.artifact_hash` становится осмысленной, потому
что `task.artifact_hash` — из БД, а `target_artifact_hash` — из подписанного
контракта.

### 4. OPA доверяет данным от агента

**Диагноз Claude.** `trusted_digest` приходит в самом запросе воркера. Флаг
`is_destructive` тоже заявляет агент, хотя в таблице угроз такой же
`destructiveHint` назван недостаточной защитой. `startswith("/workspace/task-")`
обходится через `..`.

**Решение в v0.** Отложено до v2. В v0 нет OPA, нет tool-вызовов от агентов,
нет файловых путей. Когда появится — `trusted_digest` из доверенного источника,
а не из запроса.

### 5. Вебхук — nonce не в подписи

**Диагноз Claude.** Nonce не входит в подписанный payload, поэтому replay
обходится подменой заголовка. Один HMAC-секрет на всех тенантов, а
`X-Tenant-ID` берётся из заголовка, то есть изоляция тенантов условна.
Нет лимита на `Content-Length`.

**Решение в v0.** Отложено. В v0 нет вебхуков, есть только прямое API через
SQL-функции.

### 6. Таймаут Review удаляет работу

**Диагноз Claude.** Порог алерта превращён в порог уничтожения: `git branch -D`
стирает артефакт, пока человек просто спит. Флаг `git_cleanup_ok` всегда `True`,
потому что стоит `check=False`.

**Решение в v0.** Отложено. В v0 нет Git worktree и нет Review-таймаута.
Есть `submit_review` и `verify_chain`.

### 7. Каскад однократный

**Диагноз Claude.** Затрагиваются только прямые потомки в `Ready` и
`In_Progress`. Внуки, `Review` и `Done` остаются нетронутыми, хотя текст
обещает полный откат.

**Решение в v0.** Recursive CTE в `reopen_task`. Захватывает всё поддерево,
включая `Review` и `Done`.

### 8. Проверка версии схемы пустая

**Диагноз Claude.** Скрипт сам вставляет версию 3 и тут же проверяет, что
версия ≥ 3. `REVOKE ... FROM PUBLIC` не лишает прав владельца таблицы, а
хэш-цепочки в аудит-логе нет.

**Решение в v0.** Хэш-цепочка добавлена (ADR-004). Проверка версии схемы —
не реализована в v0, отложена до миграций.

## Обмен 2: предложение Claude — «меньше движущихся частей»

Claude предложил 10 пунктов архитектурных решений. Ключевые:

1. **Postgres как единый источник истины.** Одна транзакция на переход + событие.
2. **Не писать durable execution вручную.** Делегировать Temporal/Restate
   или обойтись очередью на Postgres.
3. **Pull-модель с capabilities.** Диспетчер ранжирует, воркер сам забирает.
4. **Контракт с исполняемыми checks.** Не «LLM решит, что готово», а тесты.
5. **Артефакты по хэшу.** Git только для финального результата.
6. **Fencing token.** Без этого «воркер упал и вернулся» ломает целостность.
7. **Три уровня приёмки.** Детерминированные gates → рецензент другой модели →
   человек для рискованных переходов.
8. **Sandbox `internal: true`.** Единственный выход через gateway.
9. **Recursive cascade.** Рекурсивный запрос по всему поддереву.
10. **Hash-chained audit.** Append-only с хэш-цепочкой в отдельной роли.

Все 10 вошли в v0 (кроме 7, 8 — отложены до v2).

## Обмен 3: DDL v0 от Claude и критика моего

Claude предложил 5 таблиц и три правила целостности. Мой первоначальный DDL
имел 6 ошибок, которые Claude нашёл при чтении и прогоне:

1. **`'affinity_tags'::text[]`** — парсится как массив строк, а не поле jsonb.
2. **`NULL` в сравнении** — если `needs.min_ram_gb` отсутствует, задача
   молча отфильтровывается.
3. **`FOR UPDATE` без `OF t`** — блокирует таблицу `workers`.
4. **`check (root_id = id or root_id <> id)`** — тавтология.
5. **Хэш-цепочка без блокировки `tasks`** — `FOR UPDATE` на `events` не
   защищает первое событие.
6. **`attempts` растёт после возврата с ревью** — доработки съедают лимит
   попыток, хотя для них есть `rework`.

Все 6 исправлены в v0.

## Обмен 4: метод проверки тестов «7 поломок»

Claude внёс в схему 7 намеренных поломок по одной и проверил, какие из них
ловит набор тестов.

**Результат:**
- 5 поймано сразу: убранная блокировка в `add_dep`, убранная блокировка в
  `append_event`, `attempts` в claim, самоприёмка, каскад на один уровень.
- 2 пропущены: fencing по epoch и reclaim без `epoch + 1`.
- После анализа: `fencing по epoch` — реальная дыра в тестах, добавлен тест
  с тем же воркером и старым epoch.
- `reclaim без epoch + 1` — избыточная защита. Моё замечание снято.

**Ценность метода.** Он проверяет сами тесты, а не только код. Применяется
для v0: любой набор тестов должен ловить намеренные поломки.

## Что Claude сказал, чего я не заметил

1. **`FOR UPDATE` без `OF t`** — я не подумал, что джойн с `workers` блокирует
   обе таблицы.
2. **Порядок rate limiting** — я не проверил, что в коде он идёт до HMAC.
3. **Проверка тестов «7 поломок»** — метод, который я не применял.
4. **`attempts` растёт после ревью** — семантическая ошибка, которую я допустил
   при переносе с audited-документа.

## Что я сказал, чего Claude не заметил

1. **`artifact_hash` из параметра, не из БД** — TOCTOU в привязке согласования.
2. **Хэш-цепочка по задаче, а не глобальная** — снижает contention.
3. **Порядок внедрения v0 → v1 → v2** — безопасность идёт после работающего ядра.

## Что решили вместе

- Не отдавать агенту ТЗ на основе непроверенного SQL.
- Прогонять все спорные правки на реальном Postgres.
- Тесты — приёмочный критерий.
- Schema-first, Python — обёртка.

## Открытый вопрос

**Кто вызывает `reclaim_expired` и `promote_ready`?**
- Claude: «отдельный процесс-сторож со своим подключением и своей ролью БД».
- Я: «цикл внутри dispatcher-процесса или отдельный процесс».

**Решение в ТЗ:** отдельный процесс `swarm.watchdog`. Причины — падение
воркера не должно останавливать восстановление; несколько копий безопасны
из-за `FOR UPDATE SKIP LOCKED`.

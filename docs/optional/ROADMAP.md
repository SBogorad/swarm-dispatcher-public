# Дорожная карта v0.1 → v1.0

Документ описывает пошаговый план развития. Каждая фаза имеет:
- **Цель** — что должно работать.
- **Артефакты** — что появляется в репозитории.
- **Критерий готовности** — проверяемое условие.
- **Оценка** — рабочие дни.
- **Зависимости** — что должно быть до этой фазы.

Не переходить к следующей фазе, пока текущая не прошла критерий готовности.

---

## Обзор

| Фаза | Название | Оценка | Зависит от |
|------|----------|--------|-----------|
| **v0.1** | Работающий фундамент | ✅ Закрыта | — |
| **v0.2** | Правки v0.1 + Planner | 3–4 дня | v0.1 |
| **v0.3** | Worker с реальным LLM | 5–7 дней | v0.2 |
| **v0.4** | Веб-доска | 2–3 дня | v0.1 |
| **v0.5** | Git-интеграция | 3–4 дня | v0.3 |
| **v1.0** | Нагрузочный тест + публикация | 5–7 дней | v0.5 |

**Итого: 4–5 недель** до v1.0.

Порядок неслучаен: Planner и Worker — связанная пара. Веб-доска может идти
параллельно (независима от LLM). Git-интеграция нужна только после того,
как Worker начнёт выдавать реальные артефакты.

## v0.2 — Правки v0.1 + Planner (3–4 дня)

### Цель

Система, в которую можно подать **большую задачу текстом**, и она
**автоматически разобьёт её на граф контрактов** через LLM.

### Артефакты

- Все правки v0.1 (см. `TZ_v0.2_step1_fixes.md`) внесены.
- `crates/swarm-planner/` — новый бинарник.
- `docs/TZ_v0.2_step2_planner.md` — ТЗ выполнено.
- `tests/test_planner.py` — integration-тесты Planner.

### Критерий готовности

1. Правки v0.1 внесены, `cargo build` — зелёный, все тесты проходят.
2. `swarm-planner "Задача: сделать X"` создаёт граф из 2–10 контрактов.
3. Повторный запуск на той же задаче не создаёт дублей (idempotency).
4. Планировщик укладывается в бюджет по токенам (env `PLANNER_BUDGET`).
5. Интеграционный тест: seed → Planner разбил задачу → Worker'ы выполнили
   → задачи в `review`.

### Оценка

- Правки v0.1: 0.5 дня.
- Planner: 2–3 дня.

### Зависимости

- v0.1 (готова).
- Доступ к LLM API (OpenAI / Anthropic / локальный через llama.cpp).

## v0.3 — Worker с реальным LLM (5–7 дней)

### Цель

Воркер, который **реально выполняет работу** — вызывает LLM, обрабатывает
ответ, сохраняет артефакт в файловую систему.

### Артефакты

- `crates/swarm-worker/src/llm.rs` — обёртка над LLM (через HTTP API).
- `crates/swarm-worker/src/tools.rs` — инструменты (shell, файлы, git).
- `docs/TZ_v0.3_worker.md` — ТЗ.
- Расширенные integration-тесты с реальным LLM.

### Критерий готовности

1. Worker вызывает LLM и получает результат.
2. Результат сохраняется как **реальный файл** на диск (не только metadata).
3. `storage_path` в БД совпадает с фактическим путём файла.
4. Worker корректно обрабатывает ошибки LLM (timeout, rate limit).
5. End-to-end: Planner → Worker с LLM → артефакт на диске → review.

### Оценка

- Обёртка LLM: 1–2 дня.
- Инструменты (shell, files, git): 2 дня.
- Обработка ошибок, retry: 1–2 дня.
- Тесты: 1 день.

### Зависимости

- v0.2 (Planner).
- LLM API key или локальная модель (llama.cpp).

## v0.4 — Веб-доска (2–3 дня)

### Цель

Визуальный интерфейс: **видеть, кто взял задачу, что сделано, где застряло**.

### Артефакты

- `crates/swarm-web/` — HTTP-сервер (axum или actix-web).
- `crates/swarm-web/static/index.html` — фронтенд (vanilla JS или small).
- `docker-compose.yml` — добавлен сервис `web`.
- `docs/TZ_v0.4_web.md` — ТЗ.

### Критерий готовности

1. `GET /` — страница со списком задач (таблица с фильтрами).
2. Раз в 2 секунды данные обновляются (без перезагрузки).
3. Видно: `id`, `state`, `owner`, `epoch`, `attempts`, `created_at`.
4. `POST /add` — создать задачу через форму.
5. `POST /review/{id}` — одобрить / вернуть на доработку.
6. Работает с любого устройства в сети (телефон, планшет).

### Оценка

- HTTP-сервер: 1 день.
- Фронтенд: 1 день.
- Интеграция с compose: 0.5 дня.

### Зависимости

- v0.1 достаточно (не нужен Planner).

## v0.5 — Git-интеграция (3–4 дня)

### Цель

Артефакты сохраняются **не только в БД**, но и в **Git-репозиторий** —
с автоматическим коммитом и ссылкой на задачу.

### Артефакты

- `crates/swarm-core/src/git.rs` — обёртка над Git (через `git2` crate).
- Расширенный `save_artifact` — опциональный режим с коммитом в Git.
- `docs/TZ_v0.5_git.md` — ТЗ.

### Критерий готовности

1. При завершении задачи артефакт автоматически коммитится в Git.
2. Формат коммита: `[swarm:{task_id}] {описание}`.
3. Ссылка на коммит сохраняется в `artifacts.git_commit`.
4. Ветка настраивается через env (`SWARM_GIT_BRANCH=main`).
5. End-to-end: задача → артефакт → коммит в Git.

### Оценка

- `git2`-обёртка: 1–2 дня.
- Миграция схемы (`ALTER TABLE artifacts ADD git_commit`): 0.5 дня.
- Тесты: 1 день.

### Зависимости

- v0.3 (Worker с реальным LLM — до этого артефактов нет).

## v1.0 — Нагрузочный тест + публикация (5–7 дней)

### Цель

Публичное доказательство работоспособности: **цифры throughput, latency**,
**открытый репозиторий**, **технический отчёт**.

### Артефакты

- `bench/load_test.py` — сценарий.
- `bench/RESULTS.md` — результаты.
- `REPORT.md` — технический отчёт (для arXiv / Habr).
- `LICENSE` — MIT или Apache-2.0.
- Публичный GitHub-репозиторий.

### Критерий готовности

1. Нагрузочный тест: 1000 задач, 50 воркеров.
2. Замер: throughput (tasks/sec), latency claim (p50, p95, p99).
3. `verify_chain=true` на всех 1000 задач после завершения.
4. Технический отчёт: 15–25 страниц.
5. Открытый репозиторий, README, инструкция.

### Оценка

- Нагрузочный тест: 1–2 дня.
- Отчёт: 2–3 дня.
- Публикация: 1–2 дня.

### Зависимости

- v0.5 (полный цикл работает).

## Что НЕ входит в v1.0

Отложено сознательно:

| Что | Когда | Почему |
|-----|-------|--------|
| OPA / Policy Engine | v2.0 | Нужен только для enterprise |
| Approvals с Ed25519 | v2.0 | Нужен только для compliance |
| Мультитенантность | v2.0 | Одна организация — одна БД |
| Rate limiting | v1.1 | Не нужен без публичного API |
| Kubernetes deployment | v2.0 | Docker Compose достаточно |
| Распределённый Postgres | v2.0 | Нужен только при >1000 tasks/sec |

## Методология работы

Каждая фаза:

1. **ТЗ пишется заранее** — в `docs/TZ_vX.Y_<name>.md`.
2. **Реализация идёт по ТЗ** — без отклонений.
3. **Верификация** — независимый прогон (native + compose).
4. **Diff** — принимается только с прогоном тестов.
5. **Тег** — только после критерия готовности.

Каждая фаза оставляет **работающий код**, не «полуфабрикат». Если фаза
не завершена — не начинается следующая.

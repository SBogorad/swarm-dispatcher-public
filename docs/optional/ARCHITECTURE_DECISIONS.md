# Архитектурные решения и обоснования

Документ фиксирует решения, принятые в v0. Каждое решение имеет контекст,
альтернативы и цену. Изменение решений требует нового ADR.

---

## ADR-001: Postgres как единственный источник истины

**Решение.** Состояние задач, аренды, артефакты, события, ревью, воркеры —
в одной базе, в одной транзакции.

**Контекст.** В audited-документе (v1–v14) состояние было размазано между
SQLite, Redis (дедупликация), Git (артефакты), S3 (логи). Это давало три
класса ошибок:
1. Рассинхронизация между хранилищами (доска в одном состоянии, Git — в другом).
2. Ложноположительная идемпотентность (ключ сгорел до коммита транзакции).
3. Невозможность атомарного перехода состояния и записи события.

**Альтернативы.**
- **Redis для дедупликации** — быстрее, но даёт race при падении между `SET` и `INSERT`.
- **SQLite для одного узла** — приемлемо для одиночного воркера, но не масштабируется.
- **Event store (EventStoreDB, Kafka)** — избыточно для v0.

**Цена.** Postgres — bottleneck по throughput при росте. Решается шардированием
по `root_id` (не в v0).

**Следствия.**
- Все SQL-функции — единственная точка изменения состояния.
- Python не пишет в БД напрямую, только через функции.
- Rate limiting, лог, метрики — вне БД (реверс-прокси, OTel) или отложены.

## ADR-002: Без Redis

**Решение.** Не использовать Redis в v0. Rate limiting — на реверс-прокси
или не в v0. Кэш — не нужен (все данные горячие в Postgres).

**Контекст.** Redis использовался для:
- Дедупликации событий — заменено на `UNIQUE (task_id, event_id)`.
- Rate limiting — перенесено на реверс-прокси (или v1).
- Сессионных блокировок — не нужны, `pg_advisory_xact_lock` справляется.
- Кэша — не нужен.

**Цена.** Rate limiting на уровне приложения отсутствует. Для публичного
endpoint нужен реверс-прокси (Nginx/Envoy).

## ADR-003: Fencing token через `lease_epoch`

**Решение.** Каждая задача имеет монотонный счётчик `lease_epoch`. Любая
запись от воркера несёт `epoch`; если в БД epoch больше — запись отвергается
с `LS001`.

**Контекст.** В audited-документе был `lease_id` (UUID). Это давало дыру:
если воркер упал, потом вернулся и снова взял ту же задачу, у него снова
валидный `lease_id`, но старая операция (в параллельном потоке или до
рестарта) может записать результат.

**Почему epoch, а не UUID.**
- Монотонность: если БД говорит `epoch=5`, воркер с `epoch=3` отвергается
  независимо от того, кто он и как давно получил lease.
- Не нужно хранить историю токенов — достаточно сравнить с текущим.
- Работает при перезапуске воркера без изменения логики.

**Ссылка.** Kleppmann, M. (2016). How to do distributed locking. Классическая
аргументация: fencing token обязателен, если защищаемый ресурс (в нашем случае
запись артефакта) не поддерживает транзакционную блокировку.

**Цена.** Каждая запись должна нести `epoch`. Это добавляет один параметр
в каждый вызов (`save_artifact`, `complete_task`, `heartbeat`).

**Реализация.** `assert_lease(task_id, worker_id, epoch)` вызывается перед
любой записью. При несовпадении — `LS001`.

## ADR-004: Хэш-цепочка событий по задаче

**Решение.** Каждое событие задачи связано с предыдущим через `prev_hash` и
`hash = sha256(prev_hash || канонический_байтовый_вид_события)`.

**Контекст.** Аудит-лог должен давать **tamper-evidence** — обнаружение подмены
записей. Простой append-only лог этого не даёт: администратор БД может удалить
или изменить запись. (Non-repudiation — более сильное свойство, требует внешнего
WORM / третьей стороны; это v2.0.)

**Почему по задаче, а не глобально.**
- Глобальный advisory lock на «голову» цепочки сериализует все вставки —
  это узкое место.
- Строка `tasks` уже блокируется при переходе состояния. Логично
  использовать эту блокировку для сериализации записи в `events` по той
  же задаче.
- Форк невозможен: два параллельных события по одной задаче идут через
  `FOR UPDATE` на `tasks`, что сериализует их.

**Что даёт.**
- `verify_chain(task_id)` обнаруживает подмену.
- Для экспорта в WORM (S3 Object Lock) достаточно периодического
  подписанного чекпойнта (не в v0).

**Ограничение v0.** Цепочка не покрывает удаление всей таблицы `events`.
Для этого нужен внешний чекпойнт (WORM или подписанный файл).

## ADR-005: Pull-модель с capabilities и affinity

**Решение.** Воркер сам запрашивает задачу через `claim_task(worker_id)`.
Воркер при регистрации объявляет `capabilities` (RAM, класс модели) и
`affinity_tags`. Диспетчер ранжирует задачи по:
1. Жёсткий фильтр: `capabilities.ram_gb >= needs.min_ram_gb` и т.д.
2. Мягкое ранжирование: пересечение `affinity_tags` (чем больше, тем выше).
3. Приоритет задачи, затем FIFO.

**Контекст.** Альтернатива — push-модель (диспетчер сам назначает задачу
воркеру). Это требует:
- Знать про каждого воркера, какая у него модель загружена (холодный старт).
- Централизованно решать, кому дать задачу.
- Управлять перегрузкой.

Pull-модель проще: воркер сам решает, брать ли задачу, и делает это, когда
он свободен.

**Холодный старт.** Воркер с уже загруженной моделью помечает affinity-тег.
Задача с `needs.affinity_tags = ["model-X-loaded"]` получит приоритет у такого
воркера.

**Цена.** Диспетчер не может гарантировать SLA: если все воркеры с нужной
моделью заняты, задача ждёт. Для batch-сценария это приемлемо.

## ADR-006: Без ручного durable execution

**Решение.** Не писать Temporal/Restate вручную. Долгие операции (LLM inference)
идут вне транзакции. Аренда держится через `heartbeat` и `lease_epoch`.

**Контекст.** Классический durable execution (Temporal) требует:
- Журналирования каждого шага.
- Детерминированного replay при восстановлении.
- Управления версиями workflow.

Для задачи, где шаги — это вызовы LLM (недетерминированные), replay не
даёт воспроизводимости.

**Что делаем вместо.**
- Задача разбивается на шаги, каждый шаг — отдельная запись в `artifacts`.
- При падении воркера задача переводится в `ready` (через `reclaim_expired`),
  новый воркер начинает с последнего сохранённого артефакта.
- Воспроизводимость гарантируется на уровне `artifact_ref` (SHA-256), а не
  на уровне журнала.

**Альтернатива для тех, кому нужен Temporal.** Делегировать ретраи и саги
Temporal, а Postgres оставить как Control Plane. Это описано в audited-документе
как рекомендуемая архитектура.

## ADR-007: Schema-first, Python — обёртка

**Решение.** Вся бизнес-логика в SQL. Python вызывает функции и переводит
SQLSTATE в исключения. Никакой логики в Python, кроме валидации формы
контракта (до вызова SQL) и обёртки над ошибками.

**Контекст.** Альтернатива — реализовать логику в Python с ORM. Это даёт:
- Гибкость, но потерю атомарности.
- Возможность писать «удобные» транзакции, которые не соответствуют SQL-инвариантам.

**Цена.** Python-код менее идиоматичен (много `cursor.execute`). Разработчики
должны читать SQL, чтобы понимать поведение.

**Преимущества.**
- Единственная точка правды — SQL.
- Возможность проверить логику без Python (psql, тесты на SQL).
- Легко портировать на другой язык (Go, Rust) — просто написать обёртку.

## ADR-008: Тесты как арбитр, не мнение

**Решение.** Любое спорное утверждение проверяется запуском на реальном
Postgres. Оценки ИИ (DeepSeek, Claude) — не аргумент. Аргумент — `pytest -q`.

**Контекст.** В 14 итерациях audited-документа было много заявлений, которые
не соответствовали содержимому. Пример: «Reddit удалён» повторялось четыре
итерации подряд, пока не стало правдой. «Rate limiting после HMAC» — заявлено,
но код показывает обратное.

**Практика.**
- Все заявления об исправлениях сопровождаются ссылкой на код и тест.
- Спорные SQL-функции проверяются «7 поломок, 5 поймано, 2 добавлены» — метод
  Claude для проверки самого набора тестов.
- Если тест падает — прав Claude или DeepSeek, но не «мнение».

**Следствия.** ТЗ для агента-исполнителя включает критерий «26 passed» как
жёсткое требование. Тесты не править, чтобы прошли.

## ADR-009: Долгие задачи через мелкие артефакты

**Решение.** Одна задача может выполняться 8 часов, но состоит из шагов
по 5–30 минут. После каждого шага сохраняется `artifact` с SHA-256. При
падении воркера новый воркер продолжает с последнего артефакта.

**Контекст.** Прямолинейная реализация: открыть транзакцию на 8 часов —
убивает Postgres (VACUUM, connection pool). Открыть транзакцию на каждый
шаг — теряется контекст.

**Как работает.**
- Воркер держит аренду через `heartbeat` каждые `lease_sec/3`.
- Транзакция открывается только на мгновенные операции:
  `heartbeat`, `save_artifact`, `complete`.
- Между транзакциями воркер работает с LLM вне БД.
- При падении `lease_until < now()` → `reclaim_expired` переводит задачу
  в `ready`, следующий воркер берёт её.

**Цена.** Артефакты накапливаются. Нужна политика retention (не в v0).

## ADR-010: Отказ от OPA, Trust Registry, Approvals в v0

**Решение.** Все механизмы криптографической верификации, human-in-the-loop
с подписями, policy engine — отложены до v2.

**Контекст.** В audited-документе эти механизмы занимали 30% объёма и создавали
сложность. При этом без работающего ядра (claim, heartbeat, complete) они
бесполезны.

**Что делаем в v0.**
- Детерминированные gates (checks в контракте).
- Review с запретом self-review.
- Метка `human`/`agent` в будущей таблице `actors` — не в v0.

**Что делаем в v2.**
- `actors` с разделением human/agent.
- `approvers` с публичными ключами Ed25519.
- `approvals` с replay-защитой (`used_at`, `revoked_at`).
- OPA как PDP для авторизации tool-вызовов.
- CryptoVerifier как отдельный сервис (OPA не верифицирует подписи).

**Ссылка.** Замечание Claude: «Безопасность и комплаенс идут после работающего
ядра, а не вместе с ним. Иначе за 8 часов на слабом кластере вы получите точный
аудит того, как ничего не доехало».

## ADR-011: Порядок внедрения v0 → v1 → v2

**v0:** база, диспетчер, 2–3 воркера, детерминированные гейты, аренды с fencing.

**v1:** capabilities и affinity в полном объёме, цикл сторожа в production,
rate limiting на реверс-прокси, OTel.

**v2:** OPA, approvals с Ed25519, Trust Registry, мультитенантность.

**Критерий перехода v0 → v1:** end-to-end сценарий работает стабильно
на 3+ воркерах в течение 24 часов без ручного вмешательства.

**Критерий перехода v1 → v2:** появляются внешние пользователи или
требования compliance (EU AI Act, аудит).

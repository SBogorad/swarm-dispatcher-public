## 1. Границы применимости мультиагентной архитектуры

Применение мультиагентной схемы сопряжено с коммуникационными накладными
расходами, риском каскадных галлюцинаций и усложнением отладки. Добавление
автономных агентов и промежуточных колонок координации оправдано только
если маржинальный выигрыш в качестве, независимости проверки или
параллельной производительности превосходит совокупную стоимость
меж-агентной синхронизации.

### Когда оправдано

- **Независимая состязательная верификация (Adversarial Review).**
  Проверка кода или документации выделенным агентом-рецензентом на базе
  независимой языковой модели другого семейства. Исключает предвзятость
  модели-автора.
- **Гетерогенная специализация задач.** Разделение конвейера на этапы,
  требующие кардинально разных классов моделей, системных промптов и
  наборов инструментов (декомпозиция, генерация кода, сборка/линтинг,
  оформление документации).
- **Параллельная генерация и исследование (Fan-Out/Fan-In).**
  Одновременный запуск нескольких независимых гипотез или реализаций
  с последующим объединением результатов.

### Когда неэффективно

- **Линейные детерминированные конвейеры.** Успешно реализуются
  классическими скриптами или стандартными DAG-оркестраторами
  (Airflow, Prefect).
- **Задачи с жёсткими ограничениями по времени отклика (low-latency).**
  Пошаговая оркестрация через базу данных недопустима по требованиям SLA.
- **Монолитные задачи, контекст которых неделим.** Требуют единого окна
  внимания без промежуточных передач между моделями.

## 3. Ключевые архитектурные выводы по платформам

### Разделение уровней ответственности

Канбан-доска выступает **человеко-ориентированной плоскостью управления
(Control Plane)**, но не заменяет **распределённый движок гарантированного
исполнения (Durable Execution Engine)**. Для надёжности промышленного
уровня визуальный трекер (Plane, Planka) необходимо связывать со
специализированным слоем гарантированного выполнения шагов (Temporal,
Restate, Hatchet) либо с транзакционным диспетчером задач на Postgres.

### Формализация состояний

Жизненный цикл задачи — **Guarded FSM** (конечный автомат с охранными
условиями). Внешние события (результаты LLM, сбои инфраструктуры, решения
оператора) — дискретные триггеры переходов. Механизм **Cascading Revocation**
обеспечивает согласованный откат зависимых задач при аннулировании ранее
завершённых этапов.

### Безопасность и изоляция

`git worktree` устраняет файловые коллизии параллельной разработки,
но **не изолирует привилегии процессов ОС**. Безопасный запуск агентов
требует:
- изоляции в контейнерных песочницах (`cap_drop: ALL`, `read_only: true`,
  `no-new-privileges`);
- сетевой политики Deny-by-Default;
- авторизации каждого вызова инструментов через Policy Engine
  (Open Policy Agent);
- криптографической аутентификации подписей согласования через
  доверенный реестр ключей (Trust Registry) и модуль CryptoVerifier.

## 4. Сравнение с Durable Execution Engines

| Критерий | Kanban Control Plane | Temporal | Restate | Hatchet | Argo / Prefect |
|----------|---------------------|----------|---------|---------|----------------|
| **Назначение** | Визуализация, приоритизация, HITL | Crash-proof выполнение микрошагов | Лёгкий журнальный рантайм (Event Journaling) | Высокопроизводительный DAG-оркестратор очередей | Пакетная оркестрация контейнеров |
| **Гранулярность** | Крупноблочная (статусы колонок) | Микрошаги (функция, модель, API) | Точки выполнения системных вызовов | Шаги DAG | Контейнерные шаги |
| **Поведение при сбое** | Карточка зависает в In_Progress до таймаута | Прозрачный перезапуск с точного места | Воспроизведение из журнала | Автоматический перезапуск шага | Перезапуск пода по RestartPolicy |
| **Управление памятью** | Через артефакты задач | Нет (требует внешней БД) | Встроенное K/V | Нет | Передача артефактов через S3 |
| **HITL-интерфейс** | Нативный (drag-and-drop, веб-формы) | Программный (Signals, Queries) | Программный (Durable Promises) | Веб-интерфейс очередей | Web UI паузы пайплайна |

**Рекомендованная архитектура.** Гибридное разделение обязанностей:
Kanban-слой (Plane/Planka) отвечает за бизнес-логику задач и взаимодействие
с человеком, а оркестратор гарантированного выполнения (Temporal/Restate)
берёт на себя исполнение цепочки агентских инструментов.

Веса критериев не статичны. В зависимости от сценария приоритеты
распределяются по трём профилям.

|----------|-----|

## 7. Рекомендации по сценариям

### Корпоративный контур (EU AI Act)
**Plane (self-hosted)** + `plane-mcp-server` + Temporal/LangGraph +
OPA. Обеспечивает полный аудит вызовов, RBAC, двухэтапное согласование
HITL, crash-proof гарантии сохранения транзакций.

### Изолированный локальный кластер (R&D / Confidential)
**Hermes Agent Kanban v0.13** поверх локальной SQLite и собственных
квантованных моделей. Нулевые внешние облачные зависимости, нативный
конвейер перекрёстной верификации, автоматическое обнаружение
зомби-процессов.

### Локальная инженерная разработка с контролем через Git
**Veritas Kanban (v5.1+)** с адаптером ACP v1 и консольными средами
(Claude Code, Grok, Copilot). Физическая изоляция файлов через
`git worktree`, нативный просмотрщик диффов, регулярные контрольные точки.

### Лёгкий учёт задач для небольших команд
**Planka v2** с форком `@filcuk/planka-mcp` (40 инструментов,
Safe-by-default). Минимальное потребление памяти, авторизация по
отзываемым API-ключам.

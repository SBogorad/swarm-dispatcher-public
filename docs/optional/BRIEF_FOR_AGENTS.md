# Технический бриф для ИИ-агентов-исполнителей

Читается **первым** перед любой работой над кодом. Описывает цель,
концепцию, ограничения, критерии готовности. Если задача противоречит
брифу — остановись и спроси, не додумывай.

---

## 1. Что мы собираем

**Swarm Dispatcher** — reference implementation распределённой
оркестрации задач для сценариев, где:

- железо **слабое и гетерогенное** (разные модели, разная RAM, разный GPU);
- **latency не критична**, важна выполнимость (8 часов на задачу — приемлемо);
- задачи **декомпозируются на граф** мелких подзадач;
- воркеров **много**, каждый специализирован (модель, класс задач);
- **человек** сохраняет функцию арбитража (review, reopen, unblock).

**Что это НЕ:**

- Не замена Temporal / Restate / Airflow.
- Не интерактивный ассистент.
- Не система реального времени.
- Не «оркестратор LLM» в смысле LangGraph.

Это **Control Plane** для графа задач. Не Durable Execution Engine.

---

## 2. Зачем это нужно

### Проблема

Существующие платформы решают задачу координации одним из двух способов:

1. **Ставка на инфраструктуру.** Temporal / Restate требуют отдельный
   сервер, знание DSL, миграции. Overhead для маленькой команды.

2. **Ставка на простоту.** Kanban-доска + LLM. Работает на одной машине.
   Ломается на гетерогенном железе, при падении воркера, при большом графе.

**Никто не делает простой Postgres-first диспетчер**, который работает
на одной машине без внешних зависимостей, корректно восстанавливается
после падений, масштабируется на N машин без изменения кода, имеет
формальные инварианты.

### Идея

**MoE как физическое распределение.** В MoE роутер выбирает эксперта
под токен. У нас планировщик выбирает воркера под контракт. Разница:
эксперты в MoE гомогенны, наши воркеры гетерогенны (кодогенерация ≠
суммаризация). Это даёт выигрыш именно на слабом железе.

### Пример

8 слабых машин по 16 ГБ RAM, у каждой своя локальная модель. Задача:
рефакторинг большого проекта на 8 часов.

- **Один ноутбук**: не справится.
- **Один сервер с A100**: $30k.
- **Наш подход**: 8 машин берут по одной подзадаче, каждая со своей
  моделью. Одна упала — задача перезапускается на другой. За 8 часов
  задача доезжает.

## 3. Концепция в 6 пунктах

### 3.1. Postgres — единственный источник истины

Всё состояние (задачи, аренды, артефакты, события, ревью) в одной БД.
Переходы — атомарные транзакции. Никакого Redis, никаких очередей.

**Почему:** Redis + Postgres = два хранилища = рассинхронизация. Уже
находили баги «ключ сгорел, а коммита не было».

### 3.2. Guarded FSM

6 состояний: `pending`, `ready`, `leased`, `review`, `done`, `blocked`.
Переходы — только через SQL-функции. Guards проверяют инварианты.

### 3.3. Fencing token (`lease_epoch`)

Монотонный счётчик. Любая запись воркера несёт `epoch`. Если в БД epoch
больше — запись отвергается (`LS001`).

**Почему:** воркер упал, вернулся, снова взял задачу. У него старый
`epoch`. Без fencing он запишет неактуальный результат.

### 3.4. Pull-модель

Воркер сам забирает задачу через `claim_task()`. Диспетчер ранжирует по:

1. Жёсткий фильтр: capabilities воркера ≥ needs задачи.
2. Мягкое ранжирование: affinity-теги.
3. Приоритет задачи, FIFO.

### 3.5. Хэш-цепочка событий (tamper-evidence)

`hash = sha256(prev_hash || payload)`. `verify_chain()` проверяет
целостность. Это **tamper-evidence**, не non-repudiation (non-repudiation
требует WORM / третьей стороны, это v2.0).

### 3.6. Короткие транзакции

Долгая операция (LLM inference, 8 часов) — **вне транзакции**.
Транзакция открывается только на: `claim`, `heartbeat`, `save_artifact`,
`complete`.

## 6. Правила работы (жёсткие)

### Нельзя

- Менять `schema_v0.sql` без согласования.
- Править тесты, чтобы они прошли.
- Добавлять Redis, Kafka, OPA, Temporal в v0.x.
- Использовать `:latest` в Docker.
- Логику в Python (только CLI-обёртка опционально).
- Использовать `#[from] postgres::Error` — любой `?` обойдёт маппинг
  SQLSTATE. Только явный `map_err(DispatcherError::from_pg)`.

### Нужно

- Проверять запуском. Мнение (включая ИИ) — не аргумент.
- Schema-first. Менять SQL, потом Rust.
- Один метод = одна транзакция.
- Проверять тесты тестами (мутации).
- Фиксировать решения в ADR.
- Сборка с `--locked`.

## 7. Коды ошибок

Основные: `LS001` (LeaseLost), `GR001` (CycleDetected), `RV002` (SelfReview),
`WK002` (WorkerUnknown). Полная таблица — `docs/optional/ERRORS.md`.

Маппинг **только по `pgcode`**, не по тексту.

## 8. Технологический стек

**Postgres 16+** — единственный stateful компонент.
**Rust 1.85+** — инфраструктура.

- **`postgres` crate** (sync) — без tokio.
- **`thiserror` + `tracing`**.
- **Docker Compose** — развёртывание.
- **Python** — только CLI или внешний оркестратор (опционально).

## 11. Ключевая идея одной строкой

**Postgres-first диспетчер графа задач для слабого гетерогенного железа,

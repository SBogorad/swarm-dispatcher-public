# Аудит-бриф: `swarm-dispatcher` v0.4

**Кому:** независимому аудитору (LLM без доступа к репозиторию).
**Что на входе:** XML-тома с полным исходным кодом, инфраструктурой и документацией.
**Задача:** найти дефекты корректности, безопасности и конкурентности — с доказательствами из кода.

---

## 1. Что за проект

`swarm-dispatcher` — распределённый планировщик задач на PostgreSQL. Очередь, конечный
автомат состояний и права доступа живут **в базе** (SQL-функции `SECURITY DEFINER`), а не
в приложении. Rust-процессы — тонкие клиенты этой очереди.

Компоненты (crates):

| Крейт | Роль |
|-------|------|
| `swarm-core` | Модель данных, диспетчер, транзакции, типы |
| `swarm-planner` | Декомпозиция задачи через LLM (Planner) |
| `swarm-worker` | Исполнение подзадачи, артефакты, retry |
| `swarm-watchdog` | Возврат просроченных lease в очередь |
| `swarm-cli` | Операторский интерфейс, review |
| `swarm-llm` | Клиент LLM-провайдера |

**Ограничения проекта (соблюдать в выводах):**
- Только **синхронный** код, без async/tokio.
- Только PostgreSQL. Схема БД — источник истины.
- Публичный API `swarm-core` менять нельзя (аудит, не рефакторинг).

## 2. Как читать пакет

Тома (все — в ZIP рядом с этим брифом):

| Том | Файл | Что внутри |
|-----|------|------------|
| `CODE` | `PROJECT_CODE_BUNDLE_v0.4.xml` | Rust: 6 крейтов, src + тесты + фикстуры, Cargo |
| `INFRA` | `PROJECT_INFRA_BUNDLE_v0.4.xml` | SQL (схема/роли/патчи), init-скрипты, Dockerfile, compose, `.env.example` |
| `DOCS_CORE` | `PROJECT_DOCS_CORE_BUNDLE_v0.4.xml` | ТЗ, архитектура, известные ограничения, отчёты |
| `DOCS` | `PROJECT_DOCS_BUNDLE_v0.4.xml` | То же + методология, история решений, переписка |

**Рекомендуемый порядок:**
1. `INFRA` → `schema/schema_v0.sql`, `step2/roles.sql`, `step2b/roles_2b.sql` — сначала пойми
   автомат состояний и права.
2. `CODE` → `swarm-core` (диспетчер), затем `swarm-worker`, `swarm-watchdog`, `swarm-planner`.
3. `DOCS_CORE` → `ARCHITECTURE.md`, `KNOWN_LIMITATIONS.md` — что авторы **заявляют**.
4. Остальное — по необходимости.

**Целостность:** `CHECKSUMS_v0.4.txt` (sha256 по томам). Каждый файл внутри тома имеет
`sha256` и `md5` в `<manifest>`; полный текст — в `<content>`.

**Формат:** `<file path="…" sha256="…"><content><![CDATA[ …текст… ]]></content></file>`.

## 3. Что проверять

### 3.1. Автомат состояний и инварианты БД
Файлы: `schema/schema_v0.sql`, `step2/roles.sql`, `step2b/roles_2b.sql`, `crates/swarm-core/src/dispatcher.rs`.

- Возможны ли **состояния-сироты**: задача `claimed` без действующего lease, `done` без артефакта,
  `failed` без причины?
- Есть ли переходы, которые функция **разрешает**, но автомат не должен?
- Атомарен ли `claim`? Проверь `FOR UPDATE SKIP LOCKED` и условие выбора — нет ли окна между
  выбором строки и её обновлением.
- Может ли одна задача быть выдана **двум воркерам**?
- Согласованы ли `lease_expires_at` и системные часы (уязвимость к сдвигу времени)?

### 3.2. Конкурентность: watchdog против worker
Файлы: `crates/swarm-watchdog/src/main.rs`, `crates/swarm-worker/src/worker.rs`.

- Может ли watchdog **отобрать** задачу у живого воркера (ложное срабатывание по таймауту)?
- Что произойдёт, если воркер завершит работу **после** того, как watchdog вернул задачу в очередь?
  Двойная запись артефакта? Потеря результата?
- Есть ли защита от «зомби»-воркера (процесс жив, но не прогрессирует)?

### 3.3. Права ролей (least privilege)
Файлы: `schema/roles.sql`, `step2/roles.sql`, `step2/roles_patch_planner_status.sql`, `step2b/roles_2b.sql`.

- У каждой роли **только необходимое**? Нет ли прямого `INSERT`/`UPDATE` в таблицы в обход функций?
- `SECURITY DEFINER`-функции: зафиксирован ли `search_path`? Иначе — эскалация привилегий через
  подмену объекта.
- Может ли `swarm_worker_w1` вызвать функции планировщика (`swarm_planner`)?
- Патч грантов применяется отдельным файлом — **проверь порядок** `schema → roles → roles_2b →
  roles_patch_planner_status` и что без патча не ломается ничего, кроме ожидаемого.

### 3.4. Planner: доверие к LLM
Файлы: `crates/swarm-planner/src/parse.rs`, `lib.rs`, `prompt.rs`.

- Что при **мусорном/неполном** JSON от модели? Есть ли retry? Может ли быть бесконечный цикл?
- **Prompt injection**: текст задачи попадает в промпт внутри `<untrusted>…</untrusted>` и вырезается
  из JSON-контракта. Достаточно ли этого? Найди путь, где описание влияет на структуру плана.
- Циклические зависимости в плане: проверяются ли?
- Есть ли предел числа подзадач (защита от «плана на 10 000 шагов»)?

### 3.5. Worker: артефакты и retry
Файлы: `crates/swarm-worker/src/artifacts.rs`, `worker.rs`, `retry.rs`, `prompt.rs`.

- `sha256` артефакта считается **до** записи в БД? Может ли БД и диск разойтись (артефакт записан,
  хеш — нет, и наоборот)?
- Retry: сколько попыток? Что при падении **посередине** — остаётся частичный артефакт?
- Не перезаписывается ли артефакт предыдущей попытки?

### 3.6. Тесты: честность покрытия
Файлы: `crates/*/tests/*.rs`, `tests/test_v0.py`, `step2/test_roles.py`, `step2b/test_roles_2b.py`.

- Интеграционные тесты реально ходят в PostgreSQL или подменяют БД моками?
- Есть ли тесты **на конкурентность** (два воркера, watchdog + worker), или всё последовательно?
- Отчёты заявляют мутационное тестирование M1–M7. Проверь по тестам: воспроизводимо ли? Какие
  мутанты **выживают** (тесты их не ловят)?
- Найди утверждения в отчётах, которые код **не подтверждает**.

### 3.7. Документация против кода
Файлы: `README.md`, `docs/KNOWN_LIMITATIONS.md`, `docs/ARCHITECTURE.md`, `REPORT_*.md`.

- Проверь **честность** заявлений. Особое внимание: `KNOWN_LIMITATIONS.md` — реально ли перечислены
  все ограничения, или что-то замалчивается.
- `docs/TZ_v0.4_shell_tools_sandbox.md` — ТЗ на shell-tools и Docker-песочницу. **Реализации в этом
  бандле нет** (ожидаемо, следующая версия). Проверь только непротиворечивость ТЗ.

## 4. Чего не делать

- Не переписывать код целиком, не давать общий рефакторинг.
- Не комментировать стиль, форматирование, именование.
- Не выдумывать проблемы без **цитаты из кода**.
- Не считать, что «тесты проходят» = «код корректен». Проверяй сами тесты.

## 5. Формат ответа

Одна находка — один блок:

```
### [SEVERITY] Короткий заголовок
- Файл: путь:строка
- Суть: что не так и почему это дефект
- Доказательство: цитата кода (5–15 строк)
- Воспроизведение / проверка: как убедиться
- Предложение: минимальная правка
```

`SEVERITY`: `CRITICAL` (потеря/порча данных, эскалация прав) · `HIGH` (гонка, обход инварианта) ·
`MEDIUM` (обработка ошибок, ресурсы) · `LOW` (мелочи) · `INFO` (наблюдение).

В конце — сводка: сколько находок по severity, и **три главных риска** проекта.

Если находок нет в каком-то разделе — так и напиши: «проверено, чисто».

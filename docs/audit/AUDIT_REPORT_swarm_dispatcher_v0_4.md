### [CRITICAL] F1. Артефакты лежат в `tmpfs` каждого контейнера: результат теряется и недоступен ревьюеру
- Файл: `docker-compose.yml:75-77`, `:102-104`; `crates/swarm-worker/src/worker.rs:157-169`
- Суть: воркер пишет артефакт в `/var/swarm/artifacts`, смонтированный как `tmpfs` отдельно для каждого контейнера, и сохраняет в БД путь `storage_path`. S3 по умолчанию выключен. После рестарта контейнера файл исчезает, а строка `artifacts` и состояние `done` остаются. Другой контейнер, ревьюер или оператор файл не видит вообще. Ревью привязано к хэшу, но проверить содержимое негде.
- Доказательство:
  ```yaml
  tmpfs:
    - /var/swarm/artifacts:rw,noexec,nosuid,size=512m,uid=1001,gid=1001,mode=0755
  ```
  ```rust
  let storage_path = match ArtifactStore::from_env()? {
      Some(store) => store.put_verified(&ref_, &path, "text/plain")?,
      None => path.to_string_lossy().into_owned(),   // путь внутри контейнера воркера
  };
  ```
- Проверка: `docker compose up`, выполнить задачу до `done`, `docker compose restart worker-1`, проверить наличие файла по `artifacts.storage_path`.
- Предложение: общий именованный volume для артефактов (или обязательный S3 в стандартной конфигурации); в `save_artifact` писать только URI, который доступен всем потребителям; `KNOWN_LIMITATIONS` §1.3 заменить на реальное описание.

### [HIGH] F2. Review-gate сверяет только `type`: одна фиктивная проверка закрывает N требований
- Файл: `schema/schema_v0.sql:374-383` (и дубль в `step2/roles_patch_submit_review.sql`)
- Суть: «строгий gate» (G4/P0 #5) требует для каждого `contract.checks[i]` хотя бы один `pass` с тем же `type`. Если в контракте несколько проверок одного типа (`cmd`: `cargo test`, `cargo clippy`), достаточно одного `{"type":"cmd","status":"pass"}`. Поля `run` и любое имя проверки не сравниваются.
- Доказательство:
  ```sql
  where not exists (
    select 1 from jsonb_array_elements(p_checks) p
    where p->>'type' = c->>'type' and p->>'status' = 'pass')
  ```
- Воспроизведение (выполнено): контракт `checks=[{type:cmd,run:cargo test},{type:cmd,run:cargo clippy -- -D warnings}]`, `submit_review(..., 'approved', '[{"type":"cmd","status":"pass"}]')` → `done`. То же с одной проверкой `cargo test` и фиктивным `{"type":"cmd","status":"pass","run":"echo ok"}` → `done`.
- Предложение: сопоставлять по стабильному идентификатору проверки (`id`/индекс, задаётся в контракте и обязателен), каждый required check должен найти ровно один pass с тем же `id`; добавить в `test_review_gate.py` кейс «два check одного типа, один pass».
- Замечание: сами результаты проверок вносит рецензент, БД не проверяет, что они выполнялись. Это стоит явно записать в `KNOWN_LIMITATIONS`.

### [HIGH] F3. Идентификация воркера обходится общей ролью `swarm_worker`
- Файл: `step2b/roles_2b.sql:25-35` (`assert_worker_identity`); `step2/roles.sql:15`; `docker-compose.yml:8`
- Суть: проверка срабатывает только если `session_user LIKE 'swarm_worker_%'`. Общая роль `swarm_worker` создаётся с правом входа, её пароль обязателен в compose, и под ней любой `worker_id` принимается без проверки. Тест `test_16_common_worker_role_unchanged` закрепляет это как норму.
- **Проверка репо (2026-10-11): НЕ ВОСПРОИЗВОДИТСЯ на `e21a824`.** `alter role swarm_worker nologin` присутствует в `step2/roles.sql:21`; на чистом PG 16.15 после полного init `swarm_worker.rolcanlogin = false`, вход даёт `FATAL: role "swarm_worker" is not permitted to log in`. Тест 16 (`test_16_common_worker_role_cannot_login_or_call`) **уже** ожидает `nologin`, а не LOGIN. См. `docs/audit/evidence/f3_investigation.txt`. Аудитор, вероятно, прогонял ревизию до `nologin`-фикса.
- Воспроизведение аудитора: логин `swarm_worker` → `claim_task('victim')` вернул задачу.
- Предложение (если воспроизведётся на другой ревизии): закрыть по умолчанию, у общей роли `nologin`.

### [HIGH] F4. Сбой LLM «хоронит» задачу навсегда через фальшивый перерасход токенов
- Файл: `crates/swarm-worker/src/worker.rs:181-195`
- Суть: при исчерпании ретраев LLM воркер сдаёт `complete_task` с `overspend = cap - spent + 1`, чтобы принудительно получить `blocked`. В БД пишутся `spent_tokens > budget_cap` и причина `budget_exhausted`, хотя бюджет не тратился. `unblock_task` переводит задачу в `ready`, но `claim_task` требует `spent_tokens < budget_cap`, поэтому она никогда не выдаётся. API для сброса `spent_tokens` или повышения `budget_cap` нет.
- Доказательство:
  ```rust
  let overspend = (lease.budget_cap - lease.spent_tokens).max(0) + 1;
  let st = d.complete(lease, &ref_, overspend)?;
  ```
- Воспроизведение (выполнено): `complete_task(..., tokens=1001)` при cap 1000 → `blocked`, `spent=1001`; `unblock_task` → `ready`; `claim_task` → пусто.
- Предложение: отдельная функция «сдать с ошибкой» (`fail_task(reason)`) без искажения учёта; `unblock_task` должна уметь сбрасывать/пересчитывать `spent_tokens` или принимать новый `budget_cap`. Добавить тест «блок по ошибке LLM → unblock → claim».

### [HIGH] F5. Потеря аренды не доходит до воркера; heartbeat хрупок
- Файл: `crates/swarm-worker/src/worker.rs:101-141`, `:179`
- Суть (статически): (а) heartbeat-поток при `Ok(false)` только завершается, общего флага нет, основной поток продолжает вызывать LLM и пишет артефакт, а `complete` падает с `LS001` уже после затрат; (б) если подключение heartbeat не открылось (`:111-116`), поток молча выходит, и вся задача идёт без продления аренды; (в) при обрыве соединения `Err` логируется бесконечно, переподключения нет; (г) ветка `Err(e) if is_lease_lost(&e)` разбирает результат LLM (`:179`), который никогда не бывает `Database(LeaseLost)`, поэтому `Outcome::LeaseLost` недостижим, а реальная потеря аренды приходит как `Err` из `save_artifact`/`complete` с `?`.
- Доказательство:
  ```rust
  Ok(false) => { warn!(task_id = %task_id, "lease lost, stopping heartbeat"); break; }
  ...
  Err(e) if is_lease_lost(&e) => Outcome::LeaseLost,   // e: результат call_llm_with_retries
  ```
- Предложение: общий `AtomicBool lease_lost`, проверяемый между шагами и перед дорогими операциями; переподключение heartbeat; если heartbeat не стартовал, сдавать аренду сразу, а не работать вслепую. Проверка: тест с `Some(dsn)` и искусственным истечением аренды (сейчас таких нет, см. F14).

### [HIGH] F6. Prompt injection: разметка `<untrusted>` не экранируется, а LLM-поля лежат в «доверенной» части
- Файл: `crates/swarm-worker/src/prompt.rs:9-11`, `:31-57`; `crates/swarm-planner/src/prompt.rs:42-52`
- Суть: `wrap_untrusted` оборачивает текст без экранирования. Описание с `</untrusted>` закрывает разметку досрочно, остальное выглядит как инструкции. Поля `kind`, `checks[].run`, `needs`, порождённые LLM из недоверенного текста, идут в `contract_json` вне разметки. Планировщик вообще не размечает входной текст. Результаты инструментов в `agent_user_prompt` добавляются без пометки (косвенная инъекция через содержимое файлов).
- Доказательство:
  ```rust
  pub fn wrap_untrusted(s: &str) -> String { format!("<untrusted>{s}</untrusted>") }
  ```
  ```rust
  s.push_str(&format!("Задача: {task_text}"));   // planner, без разметки
  ```
- Предложение: заменять `<`/`>` (или выбирать разделитель со случайным нонсом), помечать `kind`/`checks`/`needs` как данные, оборачивать результаты инструментов и вход планировщика. Тест `worker_prompt_injection_inert` проверяет только наличие обёртки на безобидной строке (см. F14).

### [HIGH] F7. Planner отдаёт LLM контроль над критериями приёмки и бюджетами
- Файл: `crates/swarm-planner/src/lib.rs:82-100`; `parse.rs:150-158`
- Суть: `checks`, `needs`, `budget` подзадач берутся из ответа модели как есть, проверяется лишь непустота `checks`. Модель, направляемая инъекцией, может задать тривиальные проверки (`{"type":"cmd","run":"true"}`, как у корня), `budget.attempts` до `u32::MAX`, `needs.min_ram_gb` настолько большим, что задачу не возьмёт никто. Типы проверок не сверяются с реестром реальных гейтов.
- Доказательство:
  ```rust
  let mut budget: Budget = serde_json::from_value(t.budget.clone()).unwrap_or_default();
  if budget.attempts == 0 { budget.attempts = 3; }
  ...
  checks: t.checks.clone(),
  ```
- Предложение: реестр допустимых типов проверок и обязательные gate-проверки, назначаемые политикой, а не моделью; ограничения (clamp) на `attempts`, `max_rework`, `needs.*`; недопустимое отклонять в `validate_graph`.

### [MEDIUM] F8. Бюджет не ограничивает реальные расходы

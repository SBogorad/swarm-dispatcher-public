Архитектура открытых экосистем оркестрации автономных ИИ-агентов на базе канбан-систем и механизмов человеческого контроля
Краткое резюме (Executive Summary)
В настоящем отчете представлена инженерная спецификация и технический сравнительный анализ открытых архитектурных решений для управления группами автономных ИИ-агентов с использованием канбан-систем и механизмов контроля человеком (Human-in-the-Loop, HITL).
Главные архитектурные выводы:
Разделение уровней ответственности: Канбан-доска выступает исключительно человеко-ориентированной плоскостью управления (Control Plane), но не заменяет распределенный движок гарантированного исполнения (Durable Execution Engine). Для надежности промышленного уровня визуальный трекер (Plane, Planka) необходимо связывать со специализированным слоем гарантированного выполнения шагов (Temporal, Restate, Hatchet) или транзакционными диспетчерами задач.
Формализация состояний: Жизненный цикл задачи формализуется как конечный автомат с охранными условиями (Guarded FSM), в котором внешние события (результаты LLM, сбои инфраструктуры, решения оператора) выступают дискретными триггерами переходов. Механизм каскадной инвалидации (Cascading Revocation) обеспечивает согласованный откат зависимых задач при аннулировании ранее завершенных этапов.
Безопасность, криптография и изоляция: Механизм git worktree устраняет файловые коллизии параллельной разработки, но не изолирует привилегии процессов в операционной системе. Безопасный запуск агентов требует изоляции в контейнерных песочницах (cap_drop: ALL, read_only: true, no-new-privileges), сетевой политики Deny-by-Default, авторизации каждого вызова инструментов через Policy Engine (Open Policy Agent) и криптографической аутентификации подписей согласования через доверенный реестр ключей (Trust Registry), учетную таблицу approvals и модуль CryptoVerifier.
Экономика и токеномика: Динамическая маршрутизация моделей по колонкам доски (дешевые модели для декомпозиции, reasoning-модели для кодогенерации, модели независимых вендоров для рецензирования) снижает затраты на инференс на 60–80%. Формула совокупной стоимости учитывает фактор параллелизма (\mathcal{B}, Fan-Out) и потери от простоя мощностей при ожидании действий оператора (\mathit{Cost}_{\text{HITL\_idle}}).
Глоссарий терминов и понятий
Control Plane (Плоскость управления): Архитектурный контур, отвечающий за хранение глобального состояния проекта, управление доступом, приоритизацию бэклога и предоставление интерфейса человеку-оператору.
Data Plane (Плоскость исполнения): Инфраструктурный контур выполнения вычислений, включающий непосредственный инференс моделей, запуск скриптов в песочницах и выполнение сетевых вызовов.
Guarded FSM (Конечный автомат с охранными условиями): Машина состояний, где переходы между вершинами графа инициируются дискретными событиями и санкционируются булевыми предикатами (Guards), проверяющими инварианты, лимиты бюджетов и права доступа.
Trust Registry (Реестр доверия): База данных публичных ключей согласующих лиц, связывающая идентификатор оператора (approver_id), его роль и криптографический ключ с поддержкой временных меток отзыва (revoked_at).
Approvals Registry (Реестр согласований): Неизменяемая таблица учета выданных мандатов на утверждение задач, предотвращающая повторное использование (replay) событий согласования через фиксацию отметки used_at.
CryptoVerifier (Криптографический верификатор): Выделенный программный сервис асимметричной криптографии (Ed25519), отвечающий за математическую проверку подлинности цифровых подписей артефактов и согласований, отделенный от политик авторизации.
Cascading Revocation (Каскадная инвалидация): Процедура принудительного отката зависимых задач в ориентированном ациклическом графе (DAG) в статус блокировки при регрессионном откате родительской задачи.
Lease ID (Токен аренды): Уникальный идентификатор сессии захвата задачи воркером, подтверждающий исключительное право на ее исполнение и модификацию в течение установленного срока аренды.
Artifact Hash: Контрольная сумма SHA-256 сгенерированного артефакта (диффа Git, скомпилированного пакета, отчета), однозначно фиксирующая объект проверки на этапе рецензирования.
Saga Pattern (Паттерн распределенных саг): Модель координации распределенных транзакций, в которой сбой на промежуточном этапе инициирует цепочку компенсирующих действий для аннулирования ранее произведенных внешних побочных эффектов.
Human-in-the-Loop (HITL): Архитектурный паттерн, требующий явной верификации промежуточных данных или санкционирования критических действий человеком-оператором до продолжения работы агента.
WIP Limit (Лимит незавершенной работы): Ограничение максимального объема одновременно выполняемых задач на уровне конкретного воркера или дорожки (lane), предотвращающее распыление контекста и ресурсов.
Model Context Protocol (MCP): Открытый протокол стандартизации экспорта инструментов и контекста от серверных приложений к агентским средам.
Agent Client Protocol (ACP): Протокол абстракции клиентских интерфейсов для взаимодействия с консольными средами разработки (Claude Code, OpenAI Codex CLI, Grok).
Open Policy Agent (OPA): Декларативный движок политик безопасности, валидирующий запросы на вызов инструментов по правилам на языке Rego.
WORM Storage (Write Once, Read Many): Режим неизменяемого хранения данных (например, S3 Object Lock), предотвращающий удаление или редактирование записей журнала аудита.
Границы применимости: критерии выбора агентной архитектуры
Применение мультиагентной схемы сопряжено с коммуникационными накладными расходами, риском каскадных галлюцинаций и усложнением отладки. Добавление автономных агентов и промежуточных колонок координации оправдано только в том случае, если маржинальный выигрыш в качестве, независимости проверки или параллельной производительности превосходит совокупную стоимость меж-агентной синхронизации.
Мультиагентная канбан-архитектура оправдана в следующих сценариях:
Независимая состязательная верификация (Adversarial Review): Проверка кода или документации выделенным агентом-рецензентом на базе независимой языковой модели другого семейства, исключающая предвзятость модели-автора.
Гетерогенная специализация задач: Разделение конвейера на этапы, требующие кардинально разных классов моделей, системных промптов и наборов инструментов (декомпозиция, генерация кода, сборка/линтинг, оформление документации).
Параллельная генерация и исследование (Fan-Out/Fan-In): Одновременный запуск нескольких независимых исследовательских гипотез или реализаций с последующим объединением результатов.
Мультиагентная схема неэффективна и создает избыточные риски при выполнении:
Линейных детерминированных конвейеров, успешно реализуемых классическими скриптами или стандартными DAG-оркестраторами (Airflow, Prefect).
Задач с жесткими ограничениями по времени отклика (low-latency), где пошаговая оркестрация через базу данных недопустима по требованиям SLA.
Монолитных задач, контекст которых неделим и требует единого окна внимания без промежуточных передач между моделями.

Формальная модель состояний с охранными условиями (Guarded FSM) и инварианты
Канбан-система для ИИ-агентов формализуется как конечный автомат с охранными условиями (Guarded State Machine), где дискретные переходы между состояниями активируются внешними событиями и валидируются предикатами безопасности.
Пространство состояний и схема карточки
Множество допустимых состояний задачи определяется как:
S = \{ \mathtt{Backlog}, \mathtt{Triage}, \mathtt{Todo}, \mathtt{Ready}, \mathtt{In\_Progress}, \mathtt{Review}, \mathtt{Blocked}, \mathtt{Done} \}
Каждая карточка описывается кортежем метаданных:
\mathcal{T} = \langle \mathit{id}, \mathit{tenant\_id}, \mathit{version}, \mathit{state}, \mathit{owner\_id}, \mathit{lease\_id}, \mathit{lease\_expires}, \mathit{dag\_deps}, \mathit{budget\_cap}, \mathit{spent\_tokens}, \mathit{artifact\_hash} \rangle
где:
\mathit{id} — уникальный идентификатор задачи (UUIDv4);
\mathit{tenant\_id} — идентификатор организации/рабочего пространства для мультитенантной изоляции;
\mathit{version} — монотонно возрастающий счетчик ревизии для оптимистической блокировки;
\mathit{owner\_id} — идентификатор текущего агента или человека-оператора;
\mathit{lease\_id} и \mathit{lease\_expires} — токен аренды карточки и отметка времени истечения аренды (heartbeat);
\mathit{dag\_deps} — список идентификаторов родительских задач, выполнение которых блокирует старт текущей;
\mathit{budget\_cap} и \mathit{spent\_tokens} — финансовые лимиты и фактический расход токенов;
\mathit{artifact\_hash} — криптографический хэш (SHA-256) результирующего артефакта (Git commit hash, diff, JSON-манифест).

Системные инварианты и обработка каскадных откатов
Инвариант терминальной верификации: Переход в состояние Done невозможен без наличия криптографически верифицированного манифеста сдачи, включающего успешные логи CI/CD и хэш сдаваемого коммита.
Инвариант взаимного исключения владения (Mutual Exclusion Lease): Карточка в состоянии In_Progress может иметь не более одного активного владельца \mathit{owner\_id}. Любая модификация состояния требует совпадения актуального lease_id.
Инвариант идемпотентности транзакций: Повторная доставка событий от диспетчера, вебхуков или вызовов MCP с одинаковым idempotency_key не должна приводить к повторным вызовам языковых моделей или созданию дублирующих артефактов.
Инвариант неизменяемости объекта проверки: Рецензирование и финальное одобрение строго привязаны к конкретному \mathit{artifact\_hash}. Любое изменение файлов или контекста задачи аннулирует ранее выданные согласования и сбрасывает статус проверки.
Инвариант топологической корректности графа и каскадная инвалидация: Карточка не может перейти в состояние Ready до тех пор, пока абсолютно все узлы из списка \mathit{dag\_deps} не перейдут в терминальное состояние Done. Если родительская задача откатывается из Done в In_Progress или Blocked (вследствие обнаружения регрессии или ручного вмешательства), диспетчер обязан немедленно инициировать каскадный откат (Cascading Revocation): все зависимые дочерние задачи, находящиеся в Ready или In_Progress, принудительно переводятся в Blocked с аннулированием текущих арендных токенов lease_id.
Архитектурное описание компонентов системы
Взаимодействие компонентов в производственном контуре организуется по трехуровневой схеме:
1. Контейнерная архитектура (Уровень сервисов)
Kanban Web UI (Plane / Planka): Пользовательский интерфейс владельца системы. Обеспечивает интерактивное управление бэклогом, настройку WIP-лимитов и визуализацию рабочих дорожек (swimlanes). Взаимодействует с диспетчером через вебхуки и REST API.
Webhook Receiver Microservice: Шлюз приема событий от канбан-доски. Выполняет криптографическую валидацию HMAC-SHA256 подписей по телу и tenant-контексту, проверку временных меток, ограничение частоты запросов (Rate Limiting) через атомарный конвейер Redis и дедупликацию одноразовых nonce. Транслирует валидные события с обязательной привязкой к tenant_id в базу данных.
Resilient Kanban Dispatcher: Ядро плоскости управления. Реализует Guarded FSM, атомарный захват задач (FOR UPDATE SKIP LOCKED), проверку per-worker WIP-лимитов, контроль бюджетов токенов, двухфазную идемпотентность, reclaim-процедуры, контроль задержек ревью и эскалацию сбоев в Dead Letter Queue (DLQ).
Trust Registry & CryptoVerifier Module: Выделенный криптографический сервис на базе асимметричных ключей (Ed25519), извлекающий публичные ключи согласующих лиц из доверенной таблицы approvers, сверяющий одноразовые мандаты в таблице approvals и математически проверяющий цифровые подписи перед фиксацией перехода Review -> Done.
Open Policy Agent (OPA Engine): Независимый движок политик безопасности (PDP). Авторизует вызовы инструментов MCP, проверяет соответствие ролей, допустимость файловых путей и блокирует деструктивные флаги в рантайме.
MCP Policy Gateway & AI Gateway: Прокси-сервис между воркерами и внешними LLM/инструментами. Обеспечивает аудит вызовов, динамический роутинг моделей, маскирование секретов и экспорт OpenTelemetry трейсов.
Worker Sandboxes (Docker Hardened): Изолированные контейнеры выполнения задач. Запускаются с непривилегированным пользователем, cap_drop: ALL, read_only: true и изолированным томом tmpfs.
Инфраструктурные хранилища: PostgreSQL (основное транзакционное хранилище задач, доверенных ключей, мандатов согласования и Append-Only аудит-лога) и Redis (брокер сообщений, кэш дедупликации и сессионные блокировки).
2. Пошаговая последовательность жизненного цикла задачи
Жизненный цикл задачи разворачивается в строгой последовательности шагов:
Создание и декомпозиция: Владелец заводит цель в колонке Backlog. Диспетчер переводит ее в Triage, где вспомогательная модель декомпозирует задачу на подзадачи с фиксацией зависимостей \mathit{dag\_deps} в статусе Todo.
Разрешение зависимостей: После перехода всех родительских задач в Done, диспетчер автоматически переводит готовую подзадачу из Todo в Ready.
Атомарный захват воркером: Свободный агент вызывает метод захвата. Диспетчер проверяет per-worker WIP-лимит и остаток бюджета, после чего атомарно переводит карточку в In_Progress, выдавая уникальный lease_id на заданный срок.
Исполнение под надзором OPA: В процессе работы воркер запрашивает вызовы MCP-инструментов. Каждый вызов проходит проверку в OPA; при подтверждении полномочий регистрируется двухфазный идемпотентный ключ, списываются токены, обновляется отметка активности (heartbeat) и выполняется действие в песочнице.
Формирование артефакта и запрос ревью: Воркер генерирует diff в ветке git worktree, прогоняет локальные тесты и вызывает процедуру запроса рецензирования с передачей \mathit{artifact\_hash}. Задача переходит в Review.
Состязательная проверка и приемка: Независимый агент-рецензент другого семейства моделей инспектирует артефакт. При отсутствии дефектов и выполнении критериев приемки формируется декларативный контракт согласования с подписью, верифицируемой модулем CryptoVerifier по открытому ключу из Trust Registry с фиксацией использования в approvals, и карточка перемещается в Done.
Обработка отказов: В случае падения воркера reclaim-процедура сбрасывает аренду и возвращает задачу в Ready. При превышении таймаута ревью карточка блокируется со сбросом арендатора и компенсационным удалением git worktree, при исчерпании 3 попыток задача перемещается в Dead Letter Queue (Blocked), а при отмене родительской задачи инициируется каскадная инвалидация.

Архитектура Human-in-the-Loop, LangGraph Time-Travel и Dify
Архитектурный риск Time-Travel в LangGraph
Фреймворк LangGraph обеспечивает сохранение состояний графа через чекпоинтеры (PostgresSaver, MemorySaver), позволяя приостанавливать выполнение и производить отладку путем возврата во времени (Time-Travel).
Однако операция отката (Replay) принудительно перезапускает выполнение всех последующих узлов графа, включая вызовы больших языковых моделей и внешних API. Из-за вероятностной природы генеративных моделей повторный проход может выдать совершенно иной результат. Это делает Time-Travel принципиально несовместимым со строгой воспроизводимостью и криптографической аттестацией артефактов, если в системе не реализовано детерминированное кэширование ответов LLM по хэшу контекста или полный snapshotting состояния памяти.

Полная формула совокупной стоимости выполнения задачи
Совокупная стоимость решения задачи учитывает прямые затраты на инференс, вызовы внешних инструментов, вычислительные ресурсы, штрафы параллелизма (Fan-Out) и финансовые потери от простоя мощностей в ожидании действий человека:
\mathit{Cost}_{\text{task}} = \sum_{b \in \mathcal{B}} \left( \mathit{Cost}_{\text{LLM}, b} + \mathit{Cost}_{\text{tools}, b} + \mathit{Cost}_{\text{compute}, b} \right) + \mathit{Cost}_{\text{retries}} + \mathit{Cost}_{\text{review}} + \mathit{Cost}_{\text{HITL\_idle}}
где:
\mathcal{B} — множество параллельных ветвей вычислений при декомпозиции (параллельный фактор Fan-Out);
\mathit{Cost}_{\text{LLM}, b} = \sum_{m} (T_{\text{in}, m} \cdot P_{\text{in}, m} + T_{\text{out}, m} \cdot P_{\text{out}, m}) — суммарные прямые затраты на инференс моделей в ветви b;
\mathit{Cost}_{\text{tools}, b} — плата за вызовы платных внешних API и сервисов данных в ветви b;
\mathit{Cost}_{\text{compute}, b} — процессорное время выполнения песочниц, тестовых стендов и сборок CI;
\mathit{Cost}_{\text{retries}} — стоимость неудачных попыток и повторных циклов при падении воркеров;
\mathit{Cost}_{\text{review}} — вычислительные затраты независимой модели-рецензента;
\mathit{Cost}_{\text{HITL\_idle}} = \sum_{i} (T_{\text{wait}, i} \cdot C_{\text{idle}, i}) — стоимость простоя зарезервированных инфраструктурных ресурсов (выделенные контейнеры, удерживаемая видеопамять GPU, заблокированные воркеры) в течение времени ожидания реакции оператора T_{\text{wait}}.

Семантические конвенции OpenTelemetry GenAI
Промышленная наблюдаемость агентных сред опирается на стандарт OpenTelemetry Semantic Conventions for Generative AI (спецификация semantic-conventions-genai):
Идентификация операций: Спаны размечаются через gen_ai.operation.name со значениями chat, invoke_agent или execute_tool.
Учет токенов и моделей: Фиксируются атрибуты gen_ai.request.model, gen_ai.provider.name, gen_ai.usage.input_tokens и gen_ai.usage.output_tokens, что позволяет агрегировать расходы вне зависимости от вендора LLM.
Трассировка инструментов: Вызовы инструментов MCP регистрируются со спанами gen_ai.tool.name, gen_ai.tool.call.id и gen_ai.tool.description.
Защита персональных данных: Тела промптов и сгенерированных ответов исключены из стандартных атрибутов спанов и передаются исключительно как опциональные события gen_ai.client.inference.operation.details с предварительным маскированием PII.
Корпоративные требования: мультитенантность, безопасность и Disaster Recovery
Мультитенантность (Multi-Tenancy): В многопользовательских средах изоляция карточек и артефактов реализуется на уровне рабочих пространств (Workspaces) и проектов с разграничением пространств имен (tenant_id). Все SQL-запросы диспетчера и политики OPA содержат фильтрацию по текущему тенанту.
Data Residency и соответствие регуляторным требованиям (EU AI Act): Для соблюдения законодательства о локализации данных инфраструктура диспетчера, базы данных PostgreSQL и хранилища артефактов развертываются в пределах заданного регионального периметра. Вызовы внешних API языковых моделей направляются через шлюзы с гарантией обработки запросов в локальной юрисдикции.
Синхронизация времени (Time Synchronization): Все таймеры аренды (lease_expires) и фиксация аудит-событий опираются на синхронизацию системных часов узлов кластера через протоколы NTP/PTP со смещением не более 10 миллисекунд, что исключает преждевременное срабатывание reclaim-процедур.
Резервное копирование и Disaster Recovery (RPO / RTO):
RPO \le 5 минут: Достигается за счет непрерывной потоковой репликации PostgreSQL WAL (Write-Ahead Logging) и периодического сброса RDB/AOF-логов Redis на защищенный том S3.
RTO \le 15 минут: Восстановление из холодного состояния осуществляется запуском инфраструктурного стека через автоматизированные сценарии с развертыванием свежего снимка базы данных и проверкой целостности схемы через schema_migrations.
Ограничение частоты вызовов (Rate Limiting и Backoff): Для защиты от блокировок внешних API шлюз mcp-policy-gateway реализует алгоритм Token Bucket с экспоненциальным откатом и случайным джиттером (Exponential Backoff with Jitter), а также автоматический выключатель (Circuit Breaker) при последовательных ошибках 429/500.
Миграции схем данных, эволюция протоколов и Chaos Engineering
Эволюция схем данных и миграции
Обновление версий платформы управления требует обеспечения непрерывной доступности и возможности бессбойного отката:
Двухфазные миграции (Expand and Contract): Добавление новых полей (например, lease_id, artifact_hash) производится с дефолтными значениями NULL, сохраняя работоспособность предыдущих версий воркеров до полного обновления логики диспетчера.
Транзакционность миграций и процедура отката (Rollback): Для реляционных СУБД (PostgreSQL) применяются парные миграционные скрипты (Up/Down) в рамках транзакционного DDL; при возникновении ошибки на любом шаге миграции транзакция откатывается автоматически. Для файловой СУБД SQLite перед применением миграций выполняется обязательное создание мгновенного теневого снимка базы (VACUUM INTO '/var/data/kanban_db_pre_migration.bak'). В случае сбоя скрипта миграции производится атомарная замена файла через системный вызов переименования, гарантируя возврат к исходному состоянию без простоя сервиса.
Тестирование обратной совместимости (Contract Testing): Перед развертыванием нового кода в продакшн конвейер CI выполняет запуск набора интеграционных тестов с предыдущей версией схемы БД, подтверждая, что старые воркеры корректно считывают обновленные структуры.

Local-First / Air-Gapped R&D: Приоритет отдается автономности / отсутствию SaaS (30%), зрелости кодовой базы (20%) и изоляции (20%). Rapid Prototyping: На первом месте простота развертывания (25%), активность сообщества (20%) и удобство UI (20%). Здесь решения вроде KaibanJS (3.65) и Veritas Kanban (3.92) показывают высокую скорость ввода в эксплуатацию, требуя минимальной настройки серверной инфраструктуры.

                   """, (now, tenant_id, approval_event_id))                # 3. Проверка оптимистической блокировки                if db_version != current_version:                    raise OptimisticLockError(f"Конфликт версий: ожидалась {current_version}, в БД {db_version}")                # 5. Проверка системного инварианта топологии графа (DAG) при переводе в Ready                if target_state == 'Ready' and dag_deps:                    cur.execute("""                        SELECT count(*) FROM tasks                        WHERE tenant_id = %s AND id = ANY(%s) AND state != 'Done';                    """, (tenant_id, dag_deps))                    unresolved = cur.fetchone()[0]                    if unresolved > 0:                        raise DAGDependencyError(f"Инвариант DAG нарушен: {unresolved} родительских задач не завершены")                # 7. Проверка системного инварианта терминальной фиксации                if target_state in ('Review', 'Done') and not (artifact_hash or current_task_artifact):                    raise ValueError(f"Переход в {target_state} требует обязательного artifact_hash")                cur.execute("""                    UPDATE tasks                    SET state = %s,                        artifact_hash = COALESCE(%s, artifact_hash),                        version = version + 1,                        updated_at = %s                    WHERE tenant_id = %s AND id = %s;                """, (target_state, artifact_hash, now, tenant_id, task_id))                cur.execute("""                    INSERT INTO task_audit_log (tenant_id, task_id, previous_state, new_state, actor_id, artifact_hash, timestamp)                    VALUES (%s, %s, %s, %s, %s, %s, %s);                """, (tenant_id, task_id, state_before, target_state, actor_id, artifact_hash or current_task_artifact, now))                # 8. Задачи с retry_count < 3 возвращаются в Ready                query_recover = """                    UPDATE tasks                    SET state = 'Ready',                        owner_id = NULL,                        lease_id = NULL,                        retry_count = retry_count + 1,                        version = version + 1,                        updated_at = %s                    WHERE tenant_id = %s                      AND state = 'In_Progress'                       AND lease_expires < %s                      AND retry_count < 3                    RETURNING id;                """                cur.execute(query_recover, (now, tenant_id, now))                recovered = cur.fetchall()                logger.info("Reconcile: восстановлено %s задач", len(recovered))                for (t_id,) in recovered:                    cur.execute("""                        INSERT INTO task_audit_log (tenant_id, task_id, previous_state, new_state, actor_id, timestamp)                        VALUES (%s, %s, 'In_Progress', 'Ready', 'SYSTEM_WATCHDOG', %s);                    """, (tenant_id, t_id, now))                # 2. Задачи с исчерпанными попытками эскалируются в Blocked (Dead Letter Queue)                query_dlq = """                    UPDATE tasks                    SET state = 'Blocked',                        owner_id = NULL,                        lease_id = NULL,                        version = version + 1,                        updated_at = %s                    WHERE tenant_id = %s                      AND state = 'In_Progress'                       AND lease_expires < %s                      AND retry_count >= 3                    RETURNING id;                """                cur.execute(query_dlq, (now, tenant_id, now))                dead_letter = cur.fetchall()                logger.warning("Reconcile DLQ: эскалировано в Blocked %s задач", len(dead_letter))                for (dlq_id,) in dead_letter:                    cur.execute("""                        INSERT INTO task_audit_log (tenant_id, task_id, previous_state, new_state, actor_id, details, timestamp)                        VALUES (%s, %s, 'In_Progress', 'Blocked', 'SYSTEM_WATCHDOG', %s, %s);                    """, (tenant_id, dlq_id, json.dumps({"reason": "max_retries_exceeded_dlq"}), now))                # 3. Задачи, зависшие в Review дольше допустимого таймаута: сброс в Blocked и очистка Git worktree                review_threshold = now - review_timeout_sec                query_review_timeout = """                    UPDATE tasks                    SET state = 'Blocked',                        owner_id = NULL,                        lease_id = NULL,                        version = version + 1,                        updated_at = %s                    WHERE tenant_id = %s                      AND state = 'Review'                      AND updated_at < %s                    RETURNING id;                """                cur.execute(query_review_timeout, (now, tenant_id, review_threshold))                review_timeouts = cur.fetchall()                logger.warning("Reconcile Review Timeout: эскалировано в Blocked %s задач", len(review_timeouts))                for (rt_id,) in review_timeouts:                    # Компенсирующее действие Саги: удаление изолированного рабочего дерева Git с указанием cwd=repo_root                    worktree_dir = f"{workspaces_root}/task-{rt_id}"                    git_cleanup_ok = False                    try:                        subprocess.run(["git", "worktree", "remove", "--force", worktree_dir],                                        cwd=repo_root, check=False, capture_output=True, timeout=15)                        subprocess.run(["git", "branch", "-D", f"task-{rt_id}"],                                        cwd=repo_root, check=False, capture_output=True, timeout=15)                        git_cleanup_ok = True                    except subprocess.TimeoutExpired:                        logger.error("Таймаут удаления Git worktree для задачи %s", rt_id)                    except Exception as e:                        logger.error("Сбой удаления Git worktree для задачи %s: %s", rt_id, e)                    cur.execute("""                        INSERT INTO task_audit_log (tenant_id, task_id, previous_state, new_state, actor_id, details, timestamp)                        VALUES (%s, %s, 'Review', 'Blocked', 'SYSTEM_WATCHDOG', %s, %s);                    """, (tenant_id, rt_id, json.dumps({"reason": "review_latency_timeout_exceeded", "git_cleanup": git_cleanup_ok}), now))                conn.commit()        except DatabaseError as e:            if conn:                conn.rollback()            logger.error("Сбой БД в процедуре reconcile_zombie: %s", e)            raise        finally:            if conn:                conn.close()

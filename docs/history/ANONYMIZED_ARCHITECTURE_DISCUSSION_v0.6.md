# Обезличенный журнал архитектурной дискуссии v0.6

Документ содержит только технические тезисы, решения и открытые вопросы. Имена людей, названия каналов, идентификаторы сообщений, адреса машин, credentials, названия организаций и рабочие данные намеренно исключены.

## Исходная идея

Слабое и неоднородное оборудование можно использовать не как единый виртуальный ускоритель, а как набор специализированных исполнителей. Большая задача делится на небольшие контракты, а control plane направляет их на устройства с подходящими возможностями. Для batch-задач принципиальная выполнимость важнее минимальной задержки.

## Принятые решения

- Архитектура называется capability-aware swarm с контрактным DAG и lease-based execution. Сравнение с MoE допустимо как метафора маршрутизации контрактов, но не как утверждение о tensor-level MoE.
- PostgreSQL остаётся blackboard и единственным источником истины в v0.x.
- Planner строит DAG; worker исполняет контракт; watchdog выполняет reclaim; reviewer принимает artifact.
- Fencing через `lease_epoch` важнее быстрого handoff: медленный cold start допустим, если stale worker не может записать результат.
- Capability matching и affinity нужны для выполнимости и разумной локальности. Тендер и ценовая оптимизация откладываются до доказательства базового handoff-протокола.
- Git подходит для исходников и финальных ревизируемых результатов. Крупные промежуточные artifacts должны передаваться по content-addressed reference, а не через Git history или большие записи в PostgreSQL.
- Динамический DAG допустим при наличии cycle check, depth/children limits, budget cap и проверки каждого нового ребра.

## Риски, которые считаются реальными

- прямой доступ удалённых workers к PostgreSQL слишком широк для hostile или multi-tenant среды;
- `worker_id` не должен быть единственным механизмом identity;
- shared artifact storage должен быть доступен после миграции задачи;
- поздний результат после reclaim обязан быть отвергнут fencing-проверкой;
- batch topology не гарантирует interactive latency.

## Отложенные этапы

1. Доказать v0.6 на двух узлах или VM с одним control plane.
2. Добавить authenticated dispatcher API, чтобы не давать remote workers прямой SQL-доступ.
3. Добавить mTLS/короткоживущие credentials, revoke и rotation.
4. Добавить нагрузочный baseline для claim/heartbeat/reclaim и artifact handoff.
5. Только затем рассматривать тендер, warm affinity и стоимость исполнения.

## Правило приватности журнала

В этот файл разрешено добавлять только обезличенные архитектурные выводы. Перед публикацией нужно удалить имена, usernames, пути к домашним каталогам, IP, DNS, hostnames, токены, DSN, содержимое задач и любые фрагменты, по которым можно восстановить рабочий контекст.

# Известные ограничения v0.1

Честный список того, что **не работает** или **работает не полностью**.
Каждое ограничение имеет: что, почему, когда исправится.

Правило: если вы нашли ограничение, которого здесь нет — добавьте.
Лучше явный список, чем ложное чувство полноты.

---

## 1. Функциональные ограничения

### 1.1. Worker — заглушка, реального LLM нет

- **Что:** `swarm-worker` вместо работы вызывает `sleep(WORK_SECONDS)`.
  Не подключается к LLM, не генерирует артефакты.
- **Почему:** v0.1 — проверка инфраструктуры, не интеллекта.
- **Когда:** v0.3 (см. `docs/ROADMAP.md`).
- **Обход:** для проверки flow использовать `WORK_SECONDS=1`.

### 1.2. Planner отсутствует

- **Что:** задачи создаются вручную (`cli seed` или через `add_task`).
  Автоматической LLM-декомпозиции большой задачи на граф контрактов нет.
- **Почему:** v0.1 — фундамент. Planner — следующий шаг.
- **Когда:** v0.2 (см. `TZ_v0.2_step2_planner.md`).

### 1.3. Артефакты не пишутся на диск

- **Что:** `save_artifact` пишет metadata в БД (`storage_path`,
  `content_type`, `size_bytes`), но **файл по этому пути не создаётся**.
- **Почему:** by design в v0.1 — проверка жизненного цикла, не хранения.
- **Когда:** v0.3 (одновременно с реальным LLM-воркером).
- **Обход:** для демонстрации flow — можно игнорировать.

### 1.4. Git-интеграция отсутствует

- **Что:** артефакты хранятся в `artifacts` (content-addressable по
  SHA-256), но не коммитятся в Git.
- **Почему:** v0.1 — инфраструктурный минимум.
- **Когда:** v0.5.

### 1.5. Веб-доска отсутствует

- **Что:** наблюдение только через `cli status` (таблица в терминале).
- **Почему:** v0.1 — CLI достаточно для проверки.
- **Когда:** v0.4.

## 2. Безопасность

### 2.1. Worker не аутентифицирован

- **Что:** `swarm-worker` подключается к Postgres с общим DSN. Любой,
  знающий пароль БД, может зарегистрироваться как воркер с любым
  `WORKER_ID`.
- **Почему:** v0.1 — доверие на уровне роли БД, а не отдельного воркера.
- **Когда:** v1.0 — `sql/roles.sql`, взаимный TLS.
- **Обход:** не публиковать порт Postgres наружу; только в локальной сети.

### 2.2. Rate limiting отсутствует

- **Что:** нет ограничения на число запросов от одного IP.
- **Почему:** нет публичного HTTP-API (только SQL).
- **Когда:** v1.0 — на реверс-прокси (Nginx/Envoy).

### 2.3. OPA / Policy Engine отсутствует

- **Что:** нет проверки, имеет ли воркер право вызывать конкретный
  инструмент. `destructiveHint` не используется.
- **Почему:** v0.1 — воркер не вызывает инструментов (кроме save_artifact).
- **Когда:** v2.0 (когда появятся tool-вызовы).

### 2.4. Approvals с Ed25519 отсутствуют

- **Что:** `submit_review` проверяет только `reviewer ≠ author`.
  Криптографической подписи ревьюера нет.
- **Почему:** v0.1 — человек-ревьюер доверенный.
- **Когда:** v2.0 (для compliance).

## 3. Масштабирование

### 3.1. Мультитенантность не поддерживается

- **Что:** одна БД — одна организация. Нет `tenant_id` в таблицах.
- **Почему:** v0.1 — одна команда, одна БД.
- **Когда:** v2.0 (если появится второй тенант).

### 3.2. Один Postgres — bottleneck

- **Что:** все транзакции идут в один Postgres. При >1000 tasks/sec
  возможен saturation.
- **Почему:** v0.1 — batch-сценарий с 8-часовыми задачами.
- **Когда:** v2.0 — шардирование по `root_id`.
- **Оценка:** не измерено (нагрузочный тест — v1.0).

### 3.3. Redis отсутствует

- **Что:** нет кэша. Все запросы идут в Postgres.
- **Почему:** v0.1 — Postgres справляется. Redis усложнил бы архитектуру.
- **Когда:** v1.x, если понадобится кэш.

## 4. Наблюдаемость

### 4.1. OpenTelemetry отсутствует

- **Что:** логи есть (`tracing`), метрик нет. Нет distributed tracing.
- **Почему:** v0.1 — логирование достаточно.
- **Когда:** v1.0.

### 4.2. Дашборда нет

- **Что:** наблюдение только через `cli status` или прямой SQL.
- **Почему:** см. 1.5.
- **Когда:** v0.4 (веб-доска).

### 4.3. Алертов нет

- **Что:** если задача застряла в `blocked`, никто не получит уведомления.
- **Почему:** v0.1 — оператор сам смотрит `cli status`.
- **Когда:** v1.x.

## 5. Эксплуатация

### 5.1. Backup / restore не реализованы

- **Что:** нет скриптов бэкапа Postgres. Нет процедуры восстановления.
- **Почему:** v0.1 — dev/research среда.
- **Когда:** перед production.
- **Обход:** `pg_dump` вручную.

### 5.2. Disaster recovery не определён

- **Что:** нет RPO/RTO. Нет процедуры восстановления после сбоя сервера.
- **Почему:** v0.1.
- **Когда:** перед production.

### 5.3. Schema migrations отсутствуют

- **Что:** `schema_v0.sql` применяется один раз при первом старте.
  Миграций между версиями нет.
- **Почему:** v0.1 — первая версия.
- **Когда:** v0.2 — как только схема изменится.
- **Обход:** для dev — снести volume и применить заново.

### 5.4. Deadlock prevention не определён

- **Что:** SQL-функции короткие (мгновенные транзакции), deadlock
  маловероятен. Но явного порядка блокировок нет.
- **Почему:** v0.1 — риск не проявлялся.
- **Когда:** при росте нагрузки — `SET lock_timeout`.

### 5.5. Docker-верификация step 1–2 — ✅ ЗАКРЫТА (2026-10-08)

- **Проверено:** `docker compose up -d --build` (полный стек),
  `scripts/02-roles.sh` + `03-roles-2b.sh` + `03-role-patches.sh`,
  раздельные DSN по ролям (watchdog/worker/cli/planner), end-to-end в
  контейнерах под реальными ролями (критерии 7–9 step 1).
- **Как разблокировано:** оператор добавил себя в группу `docker`
  (`sudo usermod -aG docker $USER`); агент работает через обёртку
  `newgrp docker` (процесс гейтвея стартовал до `usermod`).
- **Найдено и исправлено при закрытии** (реальные дефекты конфигурации,
  не логики):
  1. `.env` не содержал паролей ролей → compose не собирался.
  2. `DATABASE_URL` всех сервисов использовал суперпользователя `swarm`,
     а не роль сервиса (критерий «раздельные DSN» не выполнялся).
  3. `worker_id` был `worker-1`/`worker-2`, а step 2b требует `w1`/`w2`
     (иначе `worker_identity_mismatch`).
  4. Воркер v0.3 не получал `LLM_PROVIDER` → падал на старте.
  5. tmpfs `/var/swarm/artifacts` принадлежал root → запись артефакта
     падала `Permission denied` (uid 1001). Фикс: `uid=1001,gid=1001,mode=0755`.
  6. Сервис `cli` под `profiles: ["tools"]` не собирался при `up --build`
     → запускался 8-часовой устаревший образ.
  7. `planner` отсутствовал в Dockerfile и compose.
- **e2e-результат:** Planner (роль `swarm_planner`) → Worker (роль
  `swarm_worker_w1`) → артефакт с реальным Rust-кодом на диске (sha256
  совпал с ref) → review (роль `swarm_cli`) → `done`, `verify_chain` = true.
- **Статус:** закрыта.

### 5.6. v0.4: shell tools и Docker sandbox — реализовано, но выключено по умолчанию

- **Что:** Agent Loop (`run_shell` / `read_file` / `write_file`) с запуском
  команд в Docker-контейнере реализован (`allowlist.rs`, `sandbox.rs`,
  `agent_loop.rs`), проверен 35 unit + 9 integration тестами, мутации M1–M6
  ловятся 6 из 6.
- **Что НЕ включено по умолчанию:** `WORKER_SHELL_TOOLS=0`. Чтобы воркер мог
  создавать sandbox-контейнеры, ему нужен доступ к Docker-демону.
- **Почему это риск:** единственный способ дать воркеру Docker — смонтировать
  `/var/run/docker.sock` в его контейнер. Это фактически root на хосте:
  через сокет можно создать привилегированный контейнер и выйти наружу.
  Изоляция самого sandbox (`cap_drop ALL`, `read_only`, `network none`,
  `no-new-privileges`) защищает от **команд LLM**, но не от
  скомпрометированного воркера.
- **Как включить (осознанно):** добавить воркеру сервису
  `volumes: ["/var/run/docker.sock:/var/run/docker.sock"]` и
  `WORKER_SHELL_TOOLS=1`, предварительно собрав образ
  `docker build -t agent-sandbox:1.85 sandbox/`.
- **Когда:** в v0.4+/v1.0 — когда появится отдельный runner-хост или
  rootless-вариант (Podman / Docker rootless / sysbox).
- **Обход для проверки:** запускать `worker_sandbox`-тесты с хоста, где Docker
  доступен напрямую (именно так проверено: 9/9 passed).

### 5.7. Дублирование `submit_review` устранено — ✅ ЗАКРЫТА (2026-10-11, F16г)

- **Что было:** `submit_review` определялась **дважды** — в
  `schema/schema_v0.sql` и в `step2/roles_patch_submit_review.sql`. Патч
  применялся после схемы (`04-role-patches.sh`) и **перекрывал** её тело
  устаревшей версией. Любой фикс в схеме был мёртвым кодом: initdb побеждал
  патчем (подтверждено на свежем initdb: `has_f2_key=f`).
- **Почему это дефект:** первопричина скрытых регрессий (F16г из аудита):
  один объект имел два источника истины. Патч не нёс уникальной полезной
  нагрузки — `GRANT EXECUTE ... TO swarm_reviewer` уже в `step2/roles.sql:79`,
  а тело gate было устаревшим (обходится по `type`, см. F2).
- **Решение:** `step2/roles_patch_submit_review.sql` **удалён**; монтирование
  и вызов убраны из `scripts/acceptance_harness.sh` (в `docker-compose.yml`
  его и не было). Единственный источник истины для `submit_review` и
  `validate_contract` — `schema/schema_v0.sql`.
- **Статус:** закрыто 2026-10-11 вместе с фиксом F2/F15 (строгий review-gate:
  ключ проверки `coalesce(id, type||'|'||run)`, `type` обязателен, `id`
  опционален). Триады RED→GREEN→RED в `docs/audit/evidence/`.

### 5.8. tmpfs `/workspace` монтируется с `exec`

- **Что:** в sandbox `/workspace` — tmpfs с `exec` (иначе `cargo test`
  не может запустить собранный бинарник: Docker по умолчанию добавляет
  `noexec`).
- **Почему допустимо:** `exec` внутри изолированного контейнера без
  capabilities, без сети, с read-only корнем; выполнять можно только то,
  что воркер туда положил.
- **Когда пересмотреть:** если в sandbox появится код из недоверенного
  источника, а не только из LLM-итерации.

## 6. Совместимость

### 6.1. Rust 1.85+ обязателен

- **Что:** MSRV поднят с 1.75 до 1.85 из-за `edition2024` в транзитивной
  `block-buffer 0.12`.
- **Почему:** эволюция crates.io.
- **Обход:** обновить toolchain (`rustup update`).

### 6.2. Postgres 16+ рекомендуется

- **Что:** схема использует `jsonb`, `uuid`, `FOR UPDATE SKIP LOCKED`,
  `pg_advisory_xact_lock`. Работает с Postgres 16+, проверено на 16.4
  и 18.6.
- **Почему:** старые версии не тестировались.
- **Обход:** обновить Postgres.

# Известные ограничения v0.1

Честный список того, что **не работает** или **работает не полностью**.
Каждое ограничение имеет: что, почему, когда исправится.

Правило: если вы нашли ограничение, которого здесь нет — добавьте.
Лучше явный список, чем ложное чувство полноты.

---

## 1. Функциональные ограничения

### 1.1. Worker — реальный LLM-воркер (обновлено 2026-10-11, F16a)

- **Актуально:** `swarm-worker` вызывает LLM (`call_llm_with_retries`),
  пишет артефакт на диск, делает `save_artifact`/`complete_task`, ведёт
  фоновый heartbeat. Режим «sleep(WORK_SECONDS)» остался только как тестовый
  (`work_sec`) — не как основное поведение.
- **Устаревшая формулировка (v0.1):** «Worker — заглушка, реального LLM нет».
  Оставлена как история: тезис больше неверен.
- **См.:** `crates/swarm-worker/src/worker.rs`, `docs/ROADMAP.md`.

### 1.2. Planner реализован (обновлено 2026-10-11, F16a)

- **Актуально:** `swarm-planner` есть: LLM-декомпозиция задачи в граф
  контрактов (`crates/swarm-planner`), ручной seed тоже доступен.
- **Устаревшая формулировка (v0.1):** «Planner отсутствует» — более неверна.
- **См.:** `crates/swarm-planner/`, `TZ_v0.2_step2_planner.md`.

### 1.3. Артефакты пишутся на диск и видимы потребителю (обновлено 2026-10-11, F1)

- **Актуально:** `save_artifact` записывает файл; в compose артефакты лежат в
  **общем именованном volume** `swarm-artifacts` (`storage_path` =
  `volume://swarm-artifacts/<ref>`), видимом всем контейнерам.
- **Устаревшая формулировка (v0.1):** «Файл по этому пути не создаётся» —
  более неверна. Исторический дефект F1 (per-container tmpfs) закрыт, см. §5.9.
- **Обход:** не требуется.

### 1.4. Git-интеграция отсутствует

- **Что:** артефакты хранятся в `artifacts` (content-addressable по
  SHA-256), но не коммитятся в Git.
- **Почему:** v0.1 — инфраструктурный минимум.
- **Когда:** v0.5.

### 1.5. Веб-доска отсутствует

- **Что:** наблюдение только через `cli status` (таблица в терминале).
- **Почему:** v0.1 — CLI достаточно для проверки.
- **Когда:** v0.4.

## 2. Безопасность

### 2.1. Worker не аутентифицирован

- **Что:** `swarm-worker` подключается к Postgres с общим DSN. Любой,
  знающий пароль БД, может зарегистрироваться как воркер с любым
  `WORKER_ID`.
- **Почему:** v0.1 — доверие на уровне роли БД, а не отдельного воркера.
- **Когда:** v1.0 — `sql/roles.sql`, взаимный TLS.
- **Обход:** не публиковать порт Postgres наружу; только в локальной сети.

### 2.2. Rate limiting отсутствует

- **Что:** нет ограничения на число запросов от одного IP.
- **Почему:** нет публичного HTTP-API (только SQL).
- **Когда:** v1.0 — на реверс-прокси (Nginx/Envoy).

### 2.3. OPA / Policy Engine отсутствует

- **Что:** нет проверки, имеет ли воркер право вызывать конкретный
  инструмент. `destructiveHint` не используется.
- **Почему:** v0.1 — воркер не вызывает инструментов (кроме save_artifact).
- **Когда:** v2.0 (когда появятся tool-вызовы).

### 2.4. Approvals с Ed25519 отсутствуют

- **Что:** `submit_review` проверяет только `reviewer ≠ author`.
  Криптографической подписи ревьюера нет.
- **Почему:** v0.1 — человек-ревьюер доверенный.
- **Когда:** v2.0 (для compliance).

### 2.5. Журнал событий не защищён триггером от UPDATE/DELETE

- **Что:** таблица `events` — append-only по контракту, но на ней нет
  триггера, запрещающего `UPDATE`/`DELETE`. Целостность держится на двух
  механизмах: (1) RBAC — внутренние функции (`append_event`, `event_hash`,
  `lock_root`) не выдаются никому, таблицы без `GRANT`; (2) `verify_chain`
  детектирует любую подделку хеш-цепочки.
- **Проверено на живом PG (Волна 5.2):** `append_event` идемпотентен по
  `event_id`; правка `payload` или `hash` → `verify_chain` = `false`.
- **Остаточный риск:** суперпользователь или владелец БД может изменить
  журнал в обход обоих механизмов (после правки ему пришлось бы ещё
  пересчитать всю цепочку — но это возможно). Это граница доверия к БД, а не
  дыра приложения.
- **Когда:** при переходе к compliance-профилю — добавить триггер `BEFORE
  UPDATE OR DELETE ON events → RAISE` и вынести `verify_chain` в мониторинг.

## 3. Масштабирование

### 3.1. Мультитенантность не поддерживается

- **Что:** одна БД — одна организация. Нет `tenant_id` в таблицах.
- **Почему:** v0.1 — одна команда, одна БД.
- **Когда:** v2.0 (если появится второй тенант).

### 3.2. Один Postgres — bottleneck

- **Что:** все транзакции идут в один Postgres. При >1000 tasks/sec
  возможен saturation.
- **Почему:** v0.1 — batch-сценарий с 8-часовыми задачами.
- **Когда:** v2.0 — шардирование по `root_id`.
- **Оценка:** не измерено (нагрузочный тест — v1.0).

### 3.3. Redis отсутствует

- **Что:** нет кэша. Все запросы идут в Postgres.
- **Почему:** v0.1 — Postgres справляется. Redis усложнил бы архитектуру.
- **Когда:** v1.x, если понадобится кэш.

## 5. Эксплуатация

### 5.1. Backup / restore — ✅ ЗАКРЫТА частично (Волна 5.2)

- **Что (было):** не было скриптов бэкапа/восстановления Postgres.
- **Сделано:** `ops/db_backup.sh` — `dump` (pg_dump --format=custom + sha256),
  `restore` (pg_restore), `verify` (восстановление дампа в новую disposable-БД,
  сверка числа задач + `verify_chain` по всем задачам, затем удаление БД).
  Шаг `backup/restore round-trip` добавлен в acceptance harness. Проверено на
  живом PG 16: позитив PASS, мусорный/обрезанный дамп -> FAIL, БД не остаётся.
- **Остаётся:** нет автоматического расписания бэкапов и нет процедуры
  восстановления всего кластера (RPO/RTO — см. 5.2). Требует production-решения.
- **Обход:** `pg_dump` вручную (как раньше).

### 5.2. Disaster recovery не определён

- **Что:** нет RPO/RTO. Нет процедуры восстановления после сбоя сервера.
- **Почему:** v0.1.
- **Когда:** перед production.

### 5.3. Schema migrations отсутствуют

- **Что:** `schema_v0.sql` применяется один раз при первом старте.
  Миграций между версиями нет.
- **Почему:** v0.1 — первая версия.
- **Когда:** v0.2 — как только схема изменится.
- **Обход:** для dev — снести volume и применить заново.

### 5.4. Deadlock prevention не определён

- **Что:** SQL-функции короткие (мгновенные транзакции), deadlock
  маловероятен. Но явного порядка блокировок нет.
- **Почему:** v0.1 — риск не проявлялся.
- **Когда:** при росте нагрузки — `SET lock_timeout`.

### 5.5. Docker-верификация step 1–2 — ✅ ЗАКРЫТА (2026-10-08)

- **Проверено:** `docker compose up -d --build` (полный стек),
  `scripts/02-roles.sh` + `03-roles-2b.sh` + `03-role-patches.sh`,
  раздельные DSN по ролям (watchdog/worker/cli/planner), end-to-end в
  контейнерах под реальными ролями (критерии 7–9 step 1).
- **Как разблокировано:** оператор добавил себя в группу `docker`
  (`sudo usermod -aG docker $USER`); агент работает через обёртку
  `newgrp docker` (процесс гейтвея стартовал до `usermod`).
- **Найдено и исправлено при закрытии** (реальные дефекты конфигурации,
  не логики):
  1. `.env` не содержал паролей ролей → compose не собирался.
  2. `DATABASE_URL` всех сервисов использовал суперпользователя `swarm`,
     а не роль сервиса (критерий «раздельные DSN» не выполнялся).
  3. `worker_id` был `worker-1`/`worker-2`, а step 2b требует `w1`/`w2`
     (иначе `worker_identity_mismatch`).
  4. Воркер v0.3 не получал `LLM_PROVIDER` → падал на старте.
  5. tmpfs `/var/swarm/artifacts` принадлежал root → запись артефакта
     падала `Permission denied` (uid 1001). Фикс: `uid=1001,gid=1001,mode=0755`.
  6. Сервис `cli` под `profiles: ["tools"]` не собирался при `up --build`
     → запускался 8-часовой устаревший образ.
  7. `planner` отсутствовал в Dockerfile и compose.
- **e2e-результат:** Planner (роль `swarm_planner`) → Worker (роль
  `swarm_worker_w1`) → артефакт с реальным Rust-кодом на диске (sha256
  совпал с ref) → review (роль `swarm_cli`) → `done`, `verify_chain` = true.
- **Статус:** закрыта.

### 5.6. v0.4: shell tools и Docker sandbox — реализовано, но выключено по умолчанию

- **Что:** Agent Loop (`run_shell` / `read_file` / `write_file`) с запуском
  команд в Docker-контейнере реализован (`allowlist.rs`, `sandbox.rs`,
  `agent_loop.rs`), проверен 35 unit + 9 integration тестами, мутации M1–M6
  ловятся 6 из 6.
- **Компиляционный бан (FIND-01, 2026-10-11):** модули `agent_loop`,
  `sandbox`, `allowlist`, `audit` (+ agent-промпты, `parse_step`, shell-tools
  варианты `WorkerError`) скрыты за feature **`shell-tools`**, выключенной по
  умолчанию. Бинарь `swarm-worker` её **не** включает, поэтому shell-tools
  физически **не компилируются** в бинарь воркера — бан в КОДЕ, а не в
  переписке. Проверяется арбитром в `scripts/acceptance_harness.sh`
  (`shell_tools_ban`): строит бинарь без feature и убеждается, что символы
  `AllowlistRejected` / `agent_system_prompt` / `run_shell` и т.п. отсутствуют.
  Включить для тестов/примеров: `--features swarm-worker/shell-tools`.
- **Что НЕ включено по умолчанию:** `WORKER_SHELL_TOOLS=0`. Чтобы воркер мог
  создавать sandbox-контейнеры, ему нужен доступ к Docker-демону.
- **Почему это риск:** единственный способ дать воркеру Docker — смонтировать
  `/var/run/docker.sock` в его контейнер. Это фактически root на хосте:
  через сокет можно создать привилегированный контейнер и выйти наружу.
  Изоляция самого sandbox (`cap_drop ALL`, `read_only`, `network none`,
  `no-new-privileges`) защищает от **команд LLM**, но не от
  скомпрометированного воркера.
- **Как включить (осознанно, Волна 5.2):** НЕ монтировать сокет напрямую.
  Использовать socket-proxy с белым списком Docker API
  (`ops/docker-compose.shell-tools.yml` + `ops/docker-socket-proxy.md`): воркер
  получает `DOCKER_HOST=tcp://socket-proxy:2375`, а прокси пропускает только
  `CONTAINERS/EXEC/IMAGES/INFO/PING`. Это сужает поверхность, но НЕ устраняет
  полностью (прокси фильтрует эндпоинты, не тело запроса — привилегированный
  контейнер всё ещё возможен без rootless-daemon). Включать только на выделенном
  стенде, значение `WORKER_SHELL_TOOLS=1` в базовый compose/CI НЕ добавлять.
  Прямое монтирование `/var/run/docker.sock` — только как лабораторный обход.
  Образ песочницы: `docker build -t agent-sandbox:1.85 sandbox/`.
- **Когда:** в v0.4+/v1.0 — когда появится отдельный runner-хост или
  rootless-вариант (Podman / Docker rootless / sysbox).
- **sandbox не подключён к рабочему циклу (Волна 5.2).** `Sandbox::start`/
  `stop` вызываются только в примере `examples/agent_loop_demo.rs` и тестах;
  `process_lease`/`main.rs` sandbox не запускают. То есть shell-tools
  реализованы и покрыты тестами, но в продовом пути воркера пока не встроены.
- **Следствие — утечка контейнеров при подключении.** `Sandbox` намеренно не
  удаляется в `Drop` (переживание краха воркера), а `cleanup_stale` в проде
  **не вызывается** (`grep` по коду: только тест). При встраивании sandbox в
  цикл обязательно вызывать `cleanup_stale` на старте и периодически (ТЗ §8.2
  п.9), иначе брошенные контейнеры (`sleep infinity`) копятся. Наблюдалось от
  ад-хок прогонов: 12 осиротевших `swarm-sandbox-*`, старейшие — 12 часов.
- **Обход для проверки:** запускать `worker_sandbox`-тесты с хоста, где Docker
  доступен напрямую (именно так проверено: 9/9 passed).

### 5.7. Дублирование `submit_review` устранено — ✅ ЗАКРЫТА (2026-10-11, F16г)

- **Что было:** `submit_review` определялась **дважды** — в
  `schema/schema_v0.sql` и в `step2/roles_patch_submit_review.sql`. Патч
  применялся после схемы (`04-role-patches.sh`) и **перекрывал** её тело
  устаревшей версией. Любой фикс в схеме был мёртвым кодом: initdb побеждал
  патчем (подтверждено на свежем initdb: `has_f2_key=f`).
- **Почему это дефект:** первопричина скрытых регрессий (F16г из аудита):
  один объект имел два источника истины. Патч не нёс уникальной полезной
  нагрузки — `GRANT EXECUTE ... TO swarm_reviewer` уже в `step2/roles.sql:79`,
  а тело gate было устаревшим (обходится по `type`, см. F2).
- **Решение:** `step2/roles_patch_submit_review.sql` **удалён**; монтирование
  и вызов убраны из `scripts/acceptance_harness.sh` (в `docker-compose.yml`
  его и не было). Единственный источник истины для `submit_review` и
  `validate_contract` — `schema/schema_v0.sql`.
- **Статус:** закрыто 2026-10-11 вместе с фиксом F2/F15 (строгий review-gate:
  ключ проверки `coalesce(id, type||'|'||run)`, `type` обязателен, `id`
  опционален). Триады RED→GREEN→RED в `docs/audit/evidence/`.

### 5.8. tmpfs `/workspace` монтируется с `exec`

- **Что:** в sandbox `/workspace` — tmpfs с `exec` (иначе `cargo test`
  не может запустить собранный бинарник: Docker по умолчанию добавляет
  `noexec`).
- **Почему допустимо:** `exec` внутри изолированного контейнера без
  capabilities, без сети, с read-only корнем; выполнять можно только то,
  что воркер туда положил.
- **Когда пересмотреть:** если в sandbox появится код из недоверенного
  источника, а не только из LLM-итерации.

### 5.9. Артефакты: общий volume только в пределах одного хоста — ✅ ЗАКРЫТА частично (2026-10-11, F1)

- **Что (было):** в `docker-compose.yml` `/var/swarm/artifacts` монтировался как
  **per-container tmpfs**. Файл, записанный `worker-1`, был невидим `worker-2`,
  `cli` и любому потребителю: `storage_path` указывал на container-локальный
  путь. F1 [CRITICAL].
- **Стало:** общий **именованный volume** `swarm-artifacts`, смонтированный в
  `worker-1`, `worker-2` и `cli` (потребитель). `storage_path` пишется как URI
  `volume://swarm-artifacts/<ref>` (см. `local_storage_uri` в
  `crates/swarm-worker/src/worker.rs`). Арбитр:
  `tests/test_f1_artifact_visibility.sh` — завершает задачу, перезапускает
  воркер, читает артефакт **из другого контейнера** и сверяет sha256.
- **Честный пробел (S3):** общий volume работает **только на одном хосте**.
  Для distributed-ветки (воркеры на разных машинах) нужен S3-совместимый
  store: `SWARM_ARTIFACT_S3_*` в `crates/swarm-worker/src/storage.rs`.
  По умолчанию не сконфигурирован — это осознанное ограничение, а не баг.
- **Когда пересмотреть:** при выносе воркеров на несколько хостов — включить
  S3 и заменить `ARTIFACTS_DIR`-volume на S3-режим.

### 5.10. Остаточные пункты внешнего аудита v0.4 (F8/F9/F10/F17/F18)

Явный статус на 2026-10-12 (Волна 5.3). Закрывать или нет — решает
владелец; здесь фиксируется как есть, чтобы не было «не упомянуто».

- **F8 (бюджет не ограничивает реальные расходы) — ЗАКРЫТО (2026-10-14).**
  Было: `spent_tokens` рос только в `complete_task`; попытка, оборвавшаяся
  после ответа LLM, но до `complete` (истёкшая аренда, падение), не
  учитывалась. `budget_cap` был у задачи, но не на граф (`root_id`).
  Фикс (миграция `011_budget_sync_and_root_cap.sql`):
    * синхронный учёт — триггер `AFTER INSERT ON llm_calls` атомарно
      увеличивает `tasks.spent_tokens` (расход не ждёт `complete`);
    * единый источник истины — `complete_task` больше не прибавляет токены
      повторно (совместимость: если строк ledger нет, `p_tokens` учитывается
      ровно один раз);
    * двойной гейт — колонка `tasks.root_budget_cap` + проверка
      `SUM(spent_tokens) WHERE root_id = X < root_budget_cap` в `claim_task`,
      `complete_task` и в воркере перед вызовом LLM (`task_budget_state`);
    * `reclaim_expired` при исчерпанном бюджете переводит задачу сразу в
      `budget_exhausted`, а не в `ready` (повторный оборот невозможен).
  Арбитр — `tests/test_f8_orphan_llm_spend.py` (краснеет на старой логике,
  зеленеет на фиксе).
- **F9 (неприрываемый `sleep` в heartbeat) — ЗАКРЫТО.** В `worker.rs:160`
  `thread::sleep(interval)` без проверки флага между шагами: `HeartbeatGuard::drop`
  ждёт до `lease_sec/3` (при 300 с — до 100 с). Прерываемый сон (шаги по 500 мс)
  уже применён в `swarm-watchdog/src/main.rs` — можно переиспользовать приём.
- **F10 (`tokio`/`aws-sdk-s3` вопреки «только sync») — ОТКРЫТО.** Воркер зависит
  от `tokio` и `aws-sdk-s3` независимо от настроек; при S3 `ArtifactStore::from_env()`
  создаёт `Runtime::new()` на каждую задачу (`storage.rs:48`). В доках не раскрыто.
- **F17 (идемпотентность planner) — ОТКРЫТО.** `deterministic_root_id` считается
  только от текста задачи (`parse.rs:104`): одинаковый текст от разных
  пользователей/контекстов даёт один `root_id` — второй запуск упрётся в PK.
- **F18 (`LlmError::Http` включает всё тело) — ОТКРЫТО.** `body: String` без
  обрезки попадает в логи и fail-артефакт (`crates/swarm-llm/src/error.rs:13`).

### 5.11. Allowlist — защита в глубину, а не граница безопасности

- **Что:** `cargo run`/`test`/`build` исполняют код агента по определению;
  allowlist не может это запретить. Границей остаётся sandbox-контейнер.
- **Следствие:** пока sandbox изолирован через обычный Docker (не rootless,
  не gVisor) и не подключён к циклу воркера, подключать его в прод не следует.
  Порядок: (1) rootless или gVisor, либо отдельный хост; (2) только затем
  подключение цикла с повторным аудитом.
- **Socket-proxy:** `ops/docker-socket-proxy.md` фильтрует **эндпоинты API**,
  но не тело запроса. При включённых `CONTAINERS`+`POST` скомпрометированный
  воркер может создать контейнер с монтированием хоста. Прокси защищает от
  остального Docker API, но не от компрометации самого воркера, и слушает
  `tcp:2375` по compose-сети без аутентификации.

## 6. Совместимость

### 6.1. Rust 1.94.1+ обязателен

- **Что:** MSRV поднят с 1.75 до **1.94.1** (задан в `Cargo.toml`
  как `rust-version = "1.94.1"`) из-за `edition2024` в транзитивной
  `block-buffer 0.12`. Ранее доки ошибочно указывали 1.85 — см. FIND-09.
- **Почему:** эволюция crates.io.
- **Обход:** обновить toolchain (`rustup update`).

### 6.2. Postgres 16+ рекомендуется

- **Что:** схема использует `jsonb`, `uuid`, `FOR UPDATE SKIP LOCKED`,
  `pg_advisory_xact_lock`. Работает с Postgres 16+, проверено на 16.4
  и 18.6.
- **Почему:** старые версии не тестировались.
- **Обход:** обновить Postgres.

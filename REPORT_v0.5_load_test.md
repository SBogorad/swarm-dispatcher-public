# Нагрузочное тестирование v0.5 — результаты

Дата выполнения: 2026-10-09. Все нагрузки выполнялись в disposable БД, не в `swarm`. До и после тестов в production-like БД `swarm` оставалась одна задача в состоянии `review`.

## Сводка

| Сценарий | Результат | Оценка |
|---|---|---|
| C1 — 1000 mock-задач, 50 workers | 1000 завершено; 200,26 tasks/s в schema-only прогоне; claim p99 1,040 с | throughput в целевом диапазоне 100–500 tasks/s, p99 <100 мс не выполнен; полноценный role-aware baseline ещё нужен |
| C2 — 100 задач, 10 реальных workers, Gemini 3.8 Flash через relay.fast | 100/100 `review`, 0 ошибок; 0,389 tasks/s; claim-to-completion p50/p95/p99 18,756/43,128/44,676 с | технически завершено; целевой throughput 2–5 tasks/s не достигнут |
| C3 — 1000 mock-задач, 10 workers, отказ 1 worker после claim | 1000/1000 `review`, 1 lease reclaimed, все verify_chain=true | lease recovery подтверждён; отказ был симулирован DB-клиентом, не убийством реального процесса/контейнера |

## C2 — реальный LLM worker

- Модель: `gemini-3.8-flash`, endpoint relay.fast, OpenAI-compatible API.
- База: отдельная `c2_gemini`, схема и роли проекта; worker credentials — `swarm_worker_w1`.
- Запрос: 100 независимых задач; 10 реальных процессов Rust `swarm-worker`.
- Результат: 100/100 задач в `review`; 100 completion events; timeout=false; 0 worker warnings/errors.
- Длительность: 257,128 с; throughput: 0,3889 задач/с.
- Claim-to-completion latency (события БД): p50=18,756 с, p95=43,128 с, p99=44,676 с (100 samples).
- В `tasks.spent_tokens` записано суммарно 193 695 токенов. Это usage, доступное через worker/БД; runner не получает детальную тарификацию relay.fast.
- Полный JSON: `bench/results/c2/a384eeecfd20.json`; логи процессов оставлены локально в `/tmp/swarm-c2/<run-id>/`.
- Однозадачный smoke до полного C2: run `9448dc26c991`, задача `review`, 2257 usage tokens, claim-to-completion 23,995 с.

Порог C2 из ТЗ (2–5 tasks/s) не выполнен: измерено около 0,39 tasks/s. Это локальный прогон на данном хосте и через relay.fast, а не универсальная оценка Gemini. Секретов или DSN в артефактах нет.

### Расходы

Зафиксировано 193 695 токенов по внутреннему счётчику worker. Стоимость в USD по этому числу вычислить нельзя: публично подтверждённый тариф relay.fast для выбранной модели и фактический provider-side usage breakdown не зафиксированы. Следовательно, нельзя утверждать, что расход уложился в лимит пользователя `$1.30`; перед повторными платными прогонами нужно сверить фактическое списание/тариф в relay.fast.

## C1 — DB/mock baseline

Schema-only C1: 1000/1000 завершены, 200,26 tasks/s, claim p50/p95/p99 = 0,077/0,348/1,040 с, пик 51 соединение. В более позднем диагностическом прогоне на DB с ролями было 53,07 tasks/s и p99 2,089 с, но workers подключались через admin DSN и прогон шёл на ранее использованной тестовой БД. Эти цифры не считать чистым role-aware baseline.

**Не выполнено:** отдельный чистый C1 с каждым worker под своей ролью; claim p99 <100 мс не достигнут. Существующий диагностический прогон не заменяет требуемого baseline.

## C3 — восстановление после отказа

На `c3_loadtest` сценарий завершил 1000/1000 задач, одна lease была отозвана watchdog и задача повторно завершена; все verify_chain=true. Прогон подтвердил восстановление lease через настоящие SQL-функции, однако worker process/container фактически не убивался: mock worker просто закрыл DB-соединение после claim. Поэтому критерий о реальном падении 10% процессов и сравнении throughput с сопоставимым baseline остаётся неподтверждённым.

## Вывод и ограничения приёмки

1. C2 на Gemini 3.8 Flash успешно обработал 100 задач без ошибок, но throughput ниже целевого в ~5–13 раз; p95 и p99 заметно выше нескольких секунд.
2. По 193 695 usage tokens нельзя вывести стоимость без тарифа/биллинга relay.fast; лимит `$1.30` не подтверждён.
3. C1 p99 threshold не пройден и чистый role-aware baseline не выполнен.
4. C3 проверил lease recovery, но не реальный crash worker/container.
5. Не оптимизировать production-код по этим данным до профилирования и закрытия методологических пробелов. UI v0.6 не начинать до приёмки нагрузочных критериев.
